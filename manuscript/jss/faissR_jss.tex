\title{\pkg{faissR}: CPU and GPU Nearest-Neighbor Search with FAISS and cuVS in \proglang{R}}
\Plaintitle{faissR: CPU and GPU Nearest-Neighbor Search with FAISS and cuVS in R}
\Shorttitle{FAISS and cuVS Nearest-Neighbor Search in \proglang{R}}

\Abstract{
Nearest-neighbor search is a computational primitive for statistical learning,
manifold methods, retrieval, and local prediction. \pkg{faissR} is an
open-source, Python-free interface to the FAISS \proglang{C++} library and,
optionally, NVIDIA CUDA and RAPIDS cuVS. A common interface provides exact,
inverted-file, product-quantization, graph, and low-dimensional searches for
Euclidean, cosine, and correlation distance. It accepts double and \pkg{float}
matrices, supports reusable indexes, performs batching and self-neighbor
removal in compiled code, and can keep nearest-neighbor buffers on an NVIDIA
GPU. An optional experimental CUDA policy, calibrated on an NVIDIA L40S for
cold full-self-search, selects a method and parameters from data shape, metric,
$k$, and a requested recall tier while returning route and evidence metadata.
Across nine datasets, 100 CPU/CUDA route-contract tests passed, independently
of the performance benchmark. Timed validation measured complete cold
self-search, while recall was audited on independently sampled query rows.
Controlled CPU comparisons and CUDA route evaluation showed substantial
dataset and workload heterogeneity: approximate search was advantageous in
some large-data settings, whereas exhaustive search remained competitive or
faster in others. We describe the metric contract, architecture, practical
interface, interoperability mechanisms, and reproducible evaluation of
\pkg{faissR}.
}

\section[Introduction]{Introduction} \label{sec:introduction}

For a reference matrix $X \in \mathbb{R}^{n \times p}$ and query matrix
$Q \in \mathbb{R}^{m \times p}$, nearest-neighbor search returns the $k$
reference rows closest to each query. The operation underlies local regression
and classification, clustering, anomaly detection, manifold learning, and
exploration of high-throughput biological measurements. Exhaustive self-search
has quadratic distance-evaluation cost, whereas approximate nearest-neighbor
(ANN) methods exchange some accuracy for lower time or memory.

Several compiled nearest-neighbor interfaces are available in the
\proglang{R} ecosystem. \fct{RANN::nn2} exposes exact or error-bounded search
with ANN k-d and box-decomposition trees, while \fct{FNN::get.knn} and
\fct{FNN::get.knnx} provide k-d-tree, cover-tree, cosine-oriented CR, and
linear brute-force searches \citep{RANN,FNN}. \fct{nabor::knn} wraps libnabo
k-d trees and the \class{WKNNF}/\class{WKNND} classes retain a tree for repeated
queries; \fct{Rnanoflann::nn} provides a nanoflann-based alternative
\citep{nabor,Rnanoflann}. Approximate-search interfaces include the Annoy index
classes in \pkg{RcppAnnoy}; \fct{hnsw\_knn}, \fct{hnsw\_build}, and
\fct{hnsw\_search} in \pkg{RcppHNSW}; and \fct{nnd\_knn},
\fct{rnnd\_build}, and \fct{rnnd\_query} in \pkg{rnndescent}
\citep{RcppAnnoy,RcppHNSW,rnndescent}. Within Bioconductor,
\pkg{BiocNeighbors} provides \fct{findKNN}, \fct{queryKNN}, and
\fct{buildIndex} as a common interface to exhaustive, k-means kNN,
vantage-point-tree, Annoy, and HNSW implementations \citep{BiocNeighbors}.
These packages establish a rich CPU-oriented R ecosystem, and \pkg{faissR} is
intended to complement rather than replace them. Its added value is the
integration, in one native \proglang{R} contract, of the broader FAISS index
family with optional cuVS execution and GPU-resident result buffers.
The comparator interfaces surveyed here return host-resident \proglang{R}
objects; none exposes a nearest-neighbor result that remains resident in
NVIDIA device memory for direct use by downstream compiled \proglang{R}
packages. Consequently, CPU algorithm families can be compared through their
public interfaces, whereas there is no like-for-like external
GPU-resident-\proglang{R} comparator for \fct{nn\_gpu}.

Table~\ref{tab:r-ecosystem} compares software scope rather than speed. The
survey covers the principal maintained CRAN and Bioconductor interfaces named
above; it is not evidence that one implementation is uniformly faster. Among
these interfaces, \pkg{faissR} is the only one that directly combines FAISS
CPU, optional FAISS GPU/cuVS routes, and an owning device-resident result
contract. We did not identify a maintained CRAN or Bioconductor package that
otherwise exposes cuVS nearest-neighbor search or GPU-resident neighbor buffers
through an R API. Several packages provide reusable CPU indexes, so reuse alone
is not claimed as unique.

FAISS implements mature exhaustive, inverted-file, product-quantization, and
graph indexes on CPUs and NVIDIA GPUs \citep{JohnsonDouzeJegou2021,DouzeEtAl2024}.
RAPIDS cuVS provides CUDA vector-search primitives and is integrated with
recent FAISS builds \citep{cuVS,FaissCuVS}. A statistically usable
\proglang{R} interface must additionally reconcile column-major double matrices
with predominantly row-major float32 libraries, define consistent metric and
ordering semantics, avoid rebuilding indexes for repeated queries, and make
device transfers explicit.

\pkg{faissR} addresses these integration problems. It is not a new ANN
algorithm; it is a common execution and evidence layer for FAISS CPU, optional
FAISS GPU, and optional direct CUDA/cuVS providers. Relative to existing
\proglang{R} nearest-neighbor interfaces, the package combines:
\begin{itemize}
\item one metric, ordering, and result contract across exhaustive Flat,
inverted-file, product-quantization, HNSW, CAGRA, and graph-refinement routes;
\item direct \pkg{float} input and compiled metric transformation, batching,
sorting, and self-neighbor removal, reducing conversion and R-side processing;
\item reusable fitted indexes and GPU resources, plus owning GPU-resident
nearest-neighbor buffers that downstream packages can consume through a public
C-callable interface without a mandatory device-to-host result copy; these are
contract-tested software capabilities, while their quantitative performance
benefits remain planned for dedicated systems audits; and
\item recall-targeted parameter selection for explicit methods and an optional
experimental L40S-calibrated CUDA policy for cold full-self-search, with
inspectable metadata for the requested and resolved
route, backend, data conversion, result residency, device transfers, and
calibration-hardware provenance.
\end{itemize}
The distinguishing contribution is this combination of FAISS/cuVS method
breadth, representation-aware execution, reusable CPU/GPU state, and auditable
routing through one \proglang{R} API. The automatic policy is an experimental
convenience rather than the principal contribution. Installed-policy evidence
in this article concerns CUDA; CPU evidence includes explicit HNSW, while CPU
and CUDA cross-fitted reconstructions are post hoc candidate-set sensitivity
analyses rather than validation of either installed policy.
The remainder of the article defines these contracts, illustrates their use,
and evaluates correctness, recall attainment, and paired execution time.

\section{Statistical and software design} \label{sec:design}

\subsection{Distances and recall}

The public metrics are Euclidean distance,
\begin{equation}
d_E(x,q)=\left\|x-q\right\|_2,
\end{equation}
cosine distance,
\begin{equation}
d_C(x,q)=1-\frac{x^\top q}{\|x\|_2\|q\|_2},
\end{equation}
and correlation distance,
\begin{equation}
d_R(x,q)=1-\frac{(x-\bar{x}\mathbf{1})^\top
(q-\bar{q}\mathbf{1})}{\|x-\bar{x}\mathbf{1}\|_2
\|q-\bar{q}\mathbf{1}\|_2}.
\end{equation}
Returned Euclidean values are on this ordinary L2 scale, not squared-L2 units;
providers that return squared L2 are square-rooted at the compiled boundary.
Cosine search therefore uses row normalization, while correlation search first
centers each row and then normalizes it. Cosine distance is undefined for an
all-zero vector, and correlation distance is undefined for a constant row.
For CPU routes, \pkg{faissR} applies an explicit computational convention to
these zero-normalized rows: two such rows have distance 0, whereas a
zero-normalized row and a nonzero row have distance 1. CPU Flat search invokes
the exact scorer for affected rows to preserve deterministic boundary-tie
handling. Explicit CUDA routes instead reject zero-vector cosine input and
constant-row correlation input with an informative error; they never copy the
data to the CPU for silent repair. These values are documented software
conventions for otherwise undefined cases, not mathematical cosine or Pearson
correlations. Every result records \code{distance\_is\_metric},
\code{distance\_semantics}, \code{distance\_comparable\_across\_queries}, and
\code{distance\_order}. The explicit \fct{nn\_metric\_preflight} scan returns
one-based zero-vector, constant-row, and non-finite row indices for both the
reference and query matrices and reports whether a requested backend will use
the CPU convention, reject the input, or remain backend-dependent under
\code{backend = "auto"}. The scan is opt-in so every search does not incur an
additional full matrix pass.

All backends reject \code{NA}, \code{NaN}, and positive or negative infinity.
FAISS/cuVS routes operate on float32 coordinates. Ordinary R doubles are
converted at the compiled boundary, so neighbors close to a rounding or tie
boundary can differ from a double-precision exhaustive calculation. For
normalized float32 routes, means and squared norms are accumulated in double
precision and normalized coordinates are stored as float32; native double
routes center and normalize in double precision. Native exact and candidate
scorers order equal distances by one-based row identifier. External providers
can choose a different identifier at an exactly tied boundary, which is why
the exhaustive audit accepts equivalent sorted distances. Its frozen
float32-equivalence rule is
$|a-b|\leq 10^{-5}+10^{-4}|b|$: the absolute term covers values close to zero
and the relative term scales with distance. This is an audit threshold, not a
search or target-recall tolerance.

The public metric vocabulary is deliberately restricted to
\code{"euclidean"}, \code{"cosine"}, and \code{"correlation"}. Legacy aliases
and other distances are rejected before provider dispatch. Method, backend, and
metric support is also checked as one contract: an explicit unsupported
combination fails without changing the metric, method, or device.
\code{nn\_capabilities(runtime = TRUE)} exposes this matrix together with local
FAISS, CUDA, and cuVS availability, allowing applications and benchmark scripts
to preflight a request.

For exact neighbor identifiers $N_i^{\star}(k)$ and candidate identifiers
$N_i(k)$, query-level recall is
\begin{equation}
r_i(k)=\frac{|N_i(k)\cap N_i^{\star}(k)|}{k},
\qquad
\bar r(k)=\frac{1}{m}\sum_{i=1}^{m}r_i(k).
\label{eq:recall}
\end{equation}
Identifier overlap alone can penalize an equally valid neighbor at a tied
$k$th boundary. We therefore also compute tie-aware query recall. Neighbors
strictly closer than the archived $k$th reference distance must match by
identifier. An unmatched returned neighbor receives boundary credit only when
exact metric rescoring places it at that boundary within the prespecified
float32 tolerance; total boundary credit is capped by the number of non-strict
reference slots. For an approximate route, \emph{validation attainment} of
tier $\tau$ requires a one-sided 95\% empirical query-bootstrap lower bound for
mean tie-aware query recall to be at least $\tau$ for every independent query
seed. The bound is the deterministic percentile from 1,000 query-level
bootstrap resamples. It quantifies uncertainty among the uniformly sampled
audited rows; because query outcomes share a reference matrix and the audited
rows are not a probability sample of future datasets, it is neither a
distribution-free guarantee nor a cross-dataset confidence statement.
Identifier-overlap recall, point tie-aware recall, the 5th percentile, median,
and minimum query-level recall, and the frequency of boundary substitutions
are retained as diagnostics. Exhaustive routes are assessed separately by a tie-aware
exactness audit and are labeled \emph{exact-audited}, not as ANN target
successes.

The public argument \code{target\_recall} accepts exactly the three requested
recall tiers 0.90, 0.95, and 0.99. Other numeric values fail validation; the
software neither rounds to the nearest tier nor interpolates parameters. Three
different labels are used. \emph{Calibration-feasible} means that a candidate
passed the point-estimate recall screen used by the archived broad grid.
\emph{Validation-attained} means that the empirical query-bootstrap lower bound
passed for every independent query seed. \emph{Point-recall-matched} means that
both routes in a controlled comparator pair had mean recall at least 0.99 in
every included replicate. Only the second is called target attainment without
qualification.

\subsection{Methods and providers}

Table~\ref{tab:methods} summarizes the method families. The public method name
describes the search strategy; returned metadata records the provider and
resolved backend. Thus a request cannot silently move from CUDA to CPU. The
suffix \code{\_style} in \method{nsg\_style}, \method{vamana\_style}, and
\method{nndescent\_style} is a scope marker, not an algorithm name. The
package-owned CPU routes are distinct graph-refinement algorithms that borrow
selected construction or pruning ideas from canonical NSG, Vamana, or
NN-descent; they are not feature-complete reproductions. They are explicitly
marked experimental in returned metadata and are excluded from the principal
comparative performance claims in this article. On CUDA,
\method{nndescent\_style} may instead resolve to the external cuVS NN-descent
implementation. Returned metadata distinguishes a package-owned derived
algorithm from a direct external-provider implementation.

The three exhaustive names are not three mathematical estimators and are not
simple aliases. They are distinct dispatch policies within one exhaustive
family: \method{exact} chooses the preferred available exhaustive provider,
\method{flat} explicitly requests a FAISS Flat index, and
\method{bruteforce} uses FAISS Flat on CPU but prefers direct cuVS brute force
on CUDA when available. More than one policy can therefore resolve to the same
provider on a particular installation. The requested name and concrete
\code{backend\_used} are both retained in result metadata.

Table~\ref{tab:exact-dispatch} makes the exhaustive dispatch policy explicit.
Metric preprocessing can change the provider's internal metric, but not the
public Euclidean, cosine, or correlation contract. If a provider required by
an explicit policy is unavailable, the call errors rather than changing
device or mathematical family.

\subsection{Data movement and fitted indexes}

Base \proglang{R} matrices are converted once to contiguous float32 storage at
the compiled boundary. Objects from \pkg{float} can bypass the double-to-float
conversion. Cosine and correlation transformations are cached when the same
data are reused. Query matrices are submitted in batches; returned identifiers
and distances are already ordered, and self-neighbor removal occurs in compiled
code.

The \fct{knn} interface builds a reusable model for classification or
regression, while \fct{predict} queries the fitted index. This distinction is
important for HNSW, IVF, and IVF-PQ because construction or training may
dominate one-call timing. On CUDA, \fct{nn\_gpu} returns an opaque
\class{faissR\_gpu\_knn} object whose neighbor buffers remain device-resident.
The explicit \fct{gpu\_knn\_to\_host} function performs transfer to ordinary
\proglang{R} matrices. Metadata include the requested and resolved method,
backend, input representation, result residency, and device-to-host copy count.
The GPU object owns its allocations through an external-pointer handle; the
published buffer pointers are non-owning. The producing device is synchronized
before return, no producer stream is exported, and consumers must retain the
owner until their own CUDA work completes. These objects are session-local and
are neither serializable indexes nor interprocess CUDA handles.
Predictive \fct{knn} and \fct{fast\_kmeans} are secondary convenience
interfaces in this article: they reuse the same compiled infrastructure, but
the empirical claims below concern nearest-neighbor search rather than
classification, regression, or clustering quality.

Figure~\ref{fig:architecture} summarizes the execution path. Provider-specific
details are confined behind dispatch; host and device-resident results retain
the same requested/resolved-route metadata even though their ownership and
materialization contracts differ.

\section[The R interface]{The \proglang{R} interface} \label{sec:interface}

Table~\ref{tab:api} maps the compact public interface to its principal return
objects. Nearest-neighbor search is the primary scope of this article;
predictive kNN and k-means are secondary convenience interfaces.

In function arguments, \code{backend} means the requested execution device
policy (CPU, CUDA, or automatic device resolution). The historical metadata
field \code{backend\_used} names the concrete resolved provider/route, such as
\code{faiss\_hnsw}; it is retained for API compatibility. Accordingly, the
article uses \emph{device} for CPU/CUDA choice and \emph{provider} for the
implementation that executed.

CPU \method{auto} is an available calibration-informed experimental policy,
not an independently validated counterpart of CUDA auto. CPU results record
and print \code{auto\_policy\_status =
"calibration\_informed\_not\_independently\_validated"}; selector claims in
this article concern CUDA unless explicitly identified as a cross-fitted CPU
sensitivity analysis.

CUDA \method{auto} is likewise explicitly experimental: it is an
L40S-calibrated policy for cold full-self-search, not a general policy for
arbitrary query counts, fitted-index reuse, hardware, or provider versions.
Its evidence and hardware-match fields should be inspected before use. The
performance results below therefore evaluate this narrowly scoped convenience
rather than treating it as a general selector guarantee.

Every host result has one row per query and one column per returned neighbor.
Duplicate observations remain distinct row identifiers, so a non-self
duplicate may correctly have distance zero. For self-search,
\code{exclude\_self = TRUE} removes only the query row identifier; if an
approximate candidate list omitted that identifier, the first $k$ non-self
candidates are retained rather than discarding another row.

The accepted in-memory contract is a dense numeric matrix/data frame or a
\pkg{float} matrix, with observations in rows. Sparse, delayed, and file-backed
representations are not searched in place; generic matrix-like objects passed
through \code{as.matrix} may be eagerly materialized and densified. Users
should explicitly materialize or batch such inputs. FAISS/cuVS routes convert
ordinary R doubles to contiguous row-major float32 storage, requiring a
temporary payload of approximately $4np$ bytes in addition to the source R
matrix and provider-owned index/workspace. Supplying \pkg{float} input can
avoid the numeric conversion where a direct adapter is available.

External-pointer indexes and GPU handles have no manual public destroy
function. Their owners release native allocations through finalizers after
becoming unreachable; consumers must not rely on garbage collection for CUDA
synchronization. \fct{saveRDS} preserves the R model and training data but not
a portable native index: after reload, \fct{predict} detects an invalid pointer
and rebuilds through the ordinary search path, which reports
\code{query\_source = "nn"} rather than \code{"fitted\_index"}. GPU-result
serialization and interprocess sharing are unsupported. Host identifiers use
R integers and CUDA identifiers use signed int32, so the public row-identifier
contract is limited to at most $2^{31}-1$ reference rows; provider and memory
limits are ordinarily reached much earlier. The supplement and package
vignette give the complete object, ownership, fallback, and persistence
contract.
The package-wide backend can be set with \fct{faissR\_backend}, an
\proglang{R} option, or an environment variable. An explicit function argument
has highest precedence, and unsupported backends fail rather than falling back.

\subsection{Installation and hardware portability}

Functional CPU builds require \proglang{C++20}, a Fortran compiler, and a
toolchain-compatible FAISS installation. \pkg{faissR} discovers FAISS through
\code{pkg-config}, standard prefixes, or \code{FAISS_HOME}; CUDA/cuVS support
is optional for CPU-only installation and becomes a fatal configure requirement
only when explicitly requested. Linux and macOS source builds are supported.
Native Windows CPU use requires an Rtools-compatible FAISS build; WSL2 is the
documented practical route for NVIDIA libraries. Automated binary builders
without compatible system libraries produce diagnostic objects that report the
missing provider rather than pretending to offer FAISS search. The package does
not vendor FAISS/cuVS and therefore requires compiler and external-library ABI
compatibility. Its downstream C-callable interface is independently versioned
as ABI 1 and checked by consumers before use.

The preflight reports one-based non-finite and zero/constant-row locations and
whether the requested backend would accept them. It does not silently change
the backend. Before a large search, users should budget for the source R
matrix, approximately $4np$ bytes of contiguous float32 provider input,
provider index/workspace, and at least $mk(4+8)$ bytes for host integer
identifiers and double distances. \pkg{float} input can avoid retaining both
double and converted input representations. Because \method{auto} does not
accept a memory limit, a constrained workflow should choose an explicit route,
use a representative pilot subset, query in application-level batches, and
monitor host or device memory externally. The package reports failures rather
than silently moving a CUDA request to CPU.

The bundled CUDA \method{auto} selector is an experimental static
L40S-calibrated heuristic for cold full-self-search.
On a different or unidentified GPU, the route remains available but emits one
warning per runtime model and records
\code{hardware_extrapolated_unvalidated}; explicit methods do not warn.
\code{tuning = "pilot"} and \code{"cache"} tune parameters within
the resolved method, not a replacement cross-method policy. This release does
not expose an end-user policy compiler with provider-version invalidation, so
claims of local route optimality are restricted to the reported L40S software
environment.

\section{Recall-aware operating-point selection} \label{sec:tuning}

Figure~\ref{fig:selector-flow} separates three choices that are easy to
conflate. \code{backend = "auto"} resolves the execution device from session
configuration and capabilities. \code{method = "auto"} invokes the
experimental cross-method policy. \code{tuning = "auto"} selects parameters
within whichever method has already been resolved. Unsupported combinations
and missing explicitly requested providers are errors; an execution failure
does not trigger silent fallback to another route.

The calibration framework applies to parameter selection for explicit CPU and
CUDA methods. Automatic method-family selection is independently evaluated
only for CUDA in this article; CPU \method{auto} remains an available software
policy without a selector-generalization claim.

Let $s$ index candidate settings for a fixed dataset, method, metric, backend,
$k$, and target $\tau$. The archived broad-grid calibration records one elapsed
time $T_s$ and one mean query recall $R_s$ from Equation~\ref{eq:recall} for
each candidate. Its point-estimate screening set is
\begin{equation}
\mathcal{F}_{\tau}=\{s: R_s\geq\tau,
\quad s\text{ completed without failure}\}.
\end{equation}
The selected setting minimizes $T_s$ over $\mathcal{F}_{\tau}$, with
deterministic tie-breaking by higher recall and candidate identifier.
Exact-audited candidates form a separate eligible class. If no approximate
candidate reaches $\tau$, metadata label the returned choice as below target;
this preserves the measured status of the selected operating point.
This screen is not called validation attainment. Independent validation uses
the empirical query-bootstrap criterion defined above; controlled provider
comparisons use the separately named point-recall-matching rule.

Method-specific grids cover search effort and representation parameters rather
than applying one generic knob. Examples include \code{ef\_search} for HNSW,
\code{nlist}/\code{nprobe} for IVF, product-quantizer dimensions for IVF-PQ,
and graph degree/search width for CAGRA. At dispatch, the resulting policy uses
the reference-set dimensions $(n,p)$, query count $m$ (reported as
\code{n\_points}), self-search versus explicit-query mode, the work estimate
$nmp$, metric, $k$, backend, target tier, and runtime capabilities. It does not
currently accept an expected number of future query batches, so it cannot
optimize explicitly for an index-construction amortization horizon.
Because data geometry and hardware are not fully described by these variables,
the selection metadata state whether a rule is directly measured or
extrapolated. On hardware unlike the calibration system, \method{auto} remains
available but should be treated as a calibration-informed default, not a
machine-specific optimum.

\section{Evaluation} \label{sec:evaluation}

\subsection{Datasets and protocol}

Nine real datasets span $873$ to $5.22$ million observations and $11$ to
$16,384$ variables (Table~\ref{tab:datasets}). COIL20 images were converted to
flattened $128\times128$ grayscale vectors \citep{Nene1996}; FashionMNIST and
MNIST combined their official training and test IDX files and flattened the
$28\times28$ pixels \citep{Xiao2017,LeCun1998}; and USPS used the 256-variable
matrix distributed with \pkg{Rdimtools} \citep{YouShung2022}. The
FR-FCM-ZYRM experiment retained 32 biological-marker channels from 102 FCS
files and applied $\operatorname{asinh}(x/5)$ \citep{VanUnen2017}. The flow18
and mass41 matrices used the supplied opt-SNE values without further
transformation \citep{Belkina2019}. ImageNet used 1,024-dimensional DINOv2
features from the ILSVRC 2012 training images, without additional scaling or
dimensionality reduction \citep{Russakovsky2015,Oquab2024}. MetRef removed
zero-sum variables and applied the documented KODAMA normalization and scaling
\citep{Cacciatore2014}. No labels entered neighbor timing or recall. The
calibration, reference, independent-query validation, and CUDA selector
campaigns used float32
input; no benchmark dataset received PCA or another dimension-reduction step.
The timed calibration and validation calls were full self-searches
($Q=X$, $m=n$, with self-neighbors excluded); elapsed time therefore includes
construction and one complete query pass. The phrase ``independent-query
within-dataset validation'' refers only to the recall audit: recall was
computed against exact references for up to 1,024 independently sampled unique
query rows, not by timing a separate query matrix. Rows were sampled without replacement
at $k=100$ and then cropped for $k\in\{15,30,50,100\}$. When $n\leq1,024$, all
rows were audited; consequently, MetRef used all 873 rows and no query was
sampled with replacement. The targets were
$\{0.90,0.95,0.99\}$, with two validation seeds and three timing repeats.
Each validation seed defines one independently sampled query set and one
recall-inference unit. The three timing repeats reuse that query set and inform
runtime dispersion and execution stability; they are collapsed within seed
and are not counted as three independent recall samples. Validation audit rows
were sampled independently from calibration audit rows, but both came from the
same named datasets. We therefore distinguish this query-replication
experiment from a leave-one-dataset-out (LOODO) analysis. For
each LOODO cell, every row from the held-out named dataset was removed before a
method family was chosen from the remaining datasets. Selection first used the
same prespecified shape group and otherwise the three nearest training datasets
in $\log(n)$--$\log(p)$ space. The held-out dataset was used only to evaluate
target attainment, timing relative to its empirical oracle, method-family
agreement, abstention, and exhaustive-selection frequency.

The exact-reference key contains
$9\times3\times3=81$ real-data records (dataset $\times$ metric $\times$
seed) and $2\times1\times3=6$ Euclidean synthetic-spatial records, for 87
records in total. The row-level dimensions, query counts, seeds, fingerprints,
providers, and CPU cross-audits are distributed in
\path{reference_record_dimensions.csv}.

The package-level CPU \method{auto} route was not completely evaluated in the
independent-query campaign. Consequently, no independent installed-policy
claim is made for CPU. Backend-specific LOODO analyses use explicit
independent-query route
measurements to evaluate cross-fitted selectors;
the installed package's compiled \method{auto} policy, which was calibrated on
the full collection, is retained only as a separate non-independent diagnostic.

Elapsed time includes public-interface transformations, index construction,
full self-search, and output construction; it is therefore end-to-end API time
for the one-shot $m=n$ workload rather than fitted-index query latency. For a
matched cell $c$, the reported speed ratio is
\begin{equation}
  S_c = \frac{T_{c,\mathrm{second\ route}}}
              {T_{c,\mathrm{first\ route}}},
  \label{eq:speed-ratio}
\end{equation}
so $S_c>1$ favors the first route named in the comparison. Cells were matched
within dataset, metric, $k$, target, seed, and repeat when both routes
completed. Ratios were then summarized within dataset before the
across-dataset median and interquartile range were calculated. This preserves
the dataset as the primary unit and avoids pooling incomparable absolute
times.

The replacement primary CPU provider comparison is prespecified as controlled
experimental pairs. One Slurm array task fixes the dataset, $k$, and comparator,
and executes
\pkg{faissR} and the comparator within the same allocation and on the same
node. The initially executed route is selected reproducibly at random for each
validation seed and order alternates over five repetitions. Each route
repetition uses an isolated \proglang{R} worker. Dataset and exact-reference
loading precede timing, followed by an untimed 128-row API warm-up; the
\pkg{faissR} fitted-index cache is then cleared. The formal provider comparison
in this article reports cold one-shot time only. Reusable-index construction
and fitted-index query benchmarking are excluded from quantitative comparisons
unless both routes pass the same fitted-query recall audit. Fitted-index reuse
is therefore demonstrated functionally in Section~\ref{sec:interface}, not
claimed as a comparative speed result. Both routes receive the same
double-precision matrix; \pkg{faissR}'s conversion to the float32
representation required by FAISS is included in its timed public call. This
controlled CPU comparison therefore measures user-visible API time, not a
float32-conditional search kernel.
The primary audit rejects any pair whose allocation, node, or opposing order
cannot be verified. GPU kernels are synchronized before timing ends. The
supplement records the software environment and complete aggregation rules.
The completed experiment passed 12 as the thread request to every public API
and set \code{OMP\_NUM\_THREADS}, \code{OPENBLAS\_NUM\_THREADS}, and
\code{MKL\_NUM\_THREADS} to 12. It did not sample active threads or retain the
Linux affinity mask, so equal requested thread limits must not be interpreted
as verified equal utilization.

Reusable-index and result-residency benefits are not part of the current
quantitative evidence. Prespecified planned experiments address these systems
questions separately rather than mixing them into algorithm comparisons. The
reusable-index protocol will record HNSW construction and fitted-query time independently at the
provider-specific configuration selected on calibration queries, then audits
recall on independent queries. Query batches contain 1, 32, and up to 1,024
rows; amortized totals and the break-even batch count against repeatedly
rebuilt Flat search will be derived from measured cold and repeated-query times.
Each planned memory cell runs in an isolated worker, so Linux \code{VmHWM} is scoped to
one cell rather than inherited from an earlier benchmark. Native external
pointers do not provide a portable serialized index, and persistence cost is
therefore reported as unsupported rather than timed.

The planned CUDA residency protocol will time three phases from the same
\class{faissR\_gpu\_knn} result: search before materialization, a kernel in a
minimal downstream package that consumes both device buffers and returns only
two checksum scalars, and explicit materialization with
\fct{gpu\_knn\_to\_host}. Process GPU memory is sampled with
\code{nvidia-smi}; host memory uses isolated-process \code{VmHWM}. Operation
order alternates across repetitions. This is a transfer decomposition, not a
comparison against a host-resident algorithm. All CUDA algorithm comparisons
elsewhere in this article use \fct{nn}, for which every compared route returns
host-resident matrices; \fct{nn\_gpu} is evaluated only in the separate
residency experiment. Until its completion, GPU residency supports an API and
ownership claim only, not a measured speed, transfer, or memory advantage.

\section{Results} \label{sec:results}

\subsection{Contract and calibration evidence}

All 48 CPU and 52 CUDA route-contract cells passed. The exact-reference archive
contained all 87 records ($81$ real-data and $6$ synthetic-spatial) for the
three public metrics and passed the identity and CPU cross-audit. Across the
three public metrics, calibration
produced 6,453 of 6,804 planned method--dataset--$k$--target operating points.
The 351 unavailable points comprised 318 CPU and 33 CUDA points: 306 reached the
48-hour limit and 45 were killed for memory exhaustion. They were concentrated
in FR-FCM-ZYRM (201), ImageNet features (144), and flow18 (6); the supplement
gives the method and metric breakdown. Of
4,725 approximate operating points, 3,653 (77.3\%) reached their requested
tier; the remaining 1,072 were retained as explicit negative evidence. A
further 1,728 exhaustive operating points were exact-audited. These results
show why method-specific feasibility must be checked rather than assumed.

Each successful candidate was timed once, so the campaign supports a
near-tie sensitivity analysis rather than replicate-level stability. Timing
margins and calibration-to-validation changes are reported in the supplement;
they show that recall transferred more reliably than single-run timing,
especially for CUDA IVF.

\subsection{Selector correctness and feasible-route regret}

Target attainment is a prerequisite for comparing feasible routes, not the
primary selector-performance result. For cell $c$, we define feasible-route
regret as
\begin{equation}
  G_c = \frac{T_{c,\mathrm{selected}}}
  {\min(T_{c,\mathrm{selected}}, T_{c,\mathrm{fastest\ eligible\ explicit}})}.
  \label{eq:selector-regret}
\end{equation}
The denominator includes the selected route itself, so $G_c\geq 1$. Eligibility
requires either an exact-audited route or an approximate route that attains the
requested tier under the empirical query-bootstrap lower-bound criterion in
every independent-query seed.

Table~\ref{tab:selector-regret} shows that the experimental installed CUDA
policy attained all 324 operating points largely by selecting exhaustive Flat,
but had median regret 1.10, 90th-percentile regret 3.38, and maximum regret
9.49. Only 42.6\% of cells were within 5\% of the empirical optimum. Thus,
recall attainment alone does not establish useful route selection. A post hoc
cross-fitted reconstruction had lower regret within a different explicit
exact/CAGRA candidate universe. Because explicit IVF was absent from that
universe, it is not a validation or corrected evaluation of the installed
Flat/IVF policy. These are cold full-self-search results and do not establish
regret for small query batches or reused indexes.

The 324 cells are nested combinations of three metrics, four values of $k$,
and three recall tiers within nine datasets. They are descriptive operating
points, not 324 independent experimental units; datasets are the primary
grouping unit. Table~\ref{tab:selector-dataset-main} therefore promotes the
installed-policy decomposition by dataset.

\subsection{Selector route interpretation}

The installed CUDA policy selected Flat in 280/324 cells and IVF in 44
Euclidean cells. Requested recall changed the method or its parameters in only
10/108 dataset--metric--$k$ strata. IVF was beneficial for three large
low-dimensional datasets but was about 7.1 times slower than explicit exact
search for ImageNet features. The complete metric-, target-, $k$-, dataset-,
and parameter-level decomposition is therefore retained in the supplement;
the main point is that this experimental policy is conservative, selectively
adaptive, and workload dependent.

\subsection{Post hoc candidate-set sensitivity analyses}

Named-dataset and grouped-domain reconstructions were used only as post hoc
sensitivity analyses because their explicit exact/CAGRA candidate universe
differs from the installed Flat/IVF policy. Named-dataset CUDA holdout had
median regret 1.00 within that alternative universe, whereas grouped cytometry
holdout increased median regret to 3.08. CPU reconstruction attained 301/324
cells but does not validate installed CPU \method{auto}. Route-confusion
tables, upper-tail regret, abstention, and domain-level results are moved to
the supplement. These analyses establish neither cross-collection nor
hardware-independent generalization.

\subsection{Matched-cell execution time}

Table~\ref{tab:paired-time} reports the primary matched CUDA ratios. The
controlled CPU experiment is retained as secondary configuration-level
evidence in the supplement. Its design audit recovered all 720 planned route
pairs; 691 completed, and all 29 execution failures were
\pkg{BiocNeighbors} time limits. Point-recall matching left 253 cold-call pairs
over seven datasets for \pkg{BiocNeighbors} and 268 pairs over eight datasets

These medians are explicitly conditional on successful, point-recall-matched
pairs. They do not assign a favorable runtime to a timeout: the figure reports

failure-aware performance profile or capped-runtime estimand was not
prespecified for this campaign and is therefore not reconstructed after seeing
the outcomes.

\section{Limitations} \label{sec:limitations}

The calibration policy is empirical. Shape descriptors do not capture
intrinsic dimension, clustering, density imbalance, duplicated observations,
ties, or anisotropy, and timing depends on
hardware and provider versions. Same-dataset recall-audit replication and CUDA
LOODO address different questions: the former tests independent audit-row
samples from the same matrices, while the
latter tests sensitivity to withholding one named dataset from method-family
selection. Related domains remain represented after several individual
holdouts, and the CUDA cross-fitted candidate set omitted explicit IVF.
Neither analysis establishes cross-domain or cross-collection generalization.
CPU
\method{auto} was not independently evaluated, so selector claims are limited
to CUDA; CPU results concern explicit HNSW. The CPU partition is
heterogeneous, and the CUDA results describe an NVIDIA L40S rather than all
accelerators. CPU provider ratios describe the controlled same-node cold-call
experiment, are restricted to point-recall-matched pairs, and compare
prespecified rather than provider-optimized HNSW configurations. Requested
thread limits were equal, but active thread use was not measured in that
completed experiment.
On unmatched CUDA hardware, \method{auto} warns visibly and labels the returned
evidence as extrapolated; metadata are not presented as local recalibration.
The pilot/cache modes optimize parameters within a method and do not learn or
persist a new route policy.
The automatic selector currently has no public memory budget, latency or build
deadline, or prohibition on exhaustive search. Users with such constraints
must request an explicit method after inspecting \fct{nn\_capabilities} and
route metadata. Thus a Flat choice can be recall-safe yet operationally
infeasible on a smaller device; resource-constrained abstention requires
validated resource models rather than an undocumented heuristic.
Although runtime dispatch accounts for query count and distinguishes self-search
from an explicit query matrix, the calibrated evidence in this article concerns
one-shot full self-search. The policy has no expected-reuse input and has not
been validated as an optimizer of build-amortized repeated-query workloads.
For repeated queries, users should fit or reuse an index and inspect the
reported cache and route metadata rather than interpreting the one-shot policy
as an amortized optimum.
GPU-resident output reduces transfer only when downstream code
can consume the opaque device buffers. The GPU result is synchronized before
handoff, but \pkg{faissR} does not export its CUDA stream or provider resource
object; cross-process use and serialization are unsupported. Quantitative
fitted-index and residency claims require their dedicated audits and are not
inferred from the cold algorithm benchmarks. Finally, the completed external
comparison evidence is deliberately secondary. The controlled HNSW experiment
covers fixed \pkg{BiocNeighbors} and \pkg{RcppHNSW} configurations;
independently tuned HNSW Pareto comparisons and the broader exact/graph
R-interface campaign require their prespecified audits before numerical claims
are added. Table~\ref{tab:r-ecosystem} therefore makes feature-level, not
speed, comparisons with the wider R ecosystem. Fitted-index reuse is tested as
a software contract, but no fitted-query speed ratio is reported without a
point-recall-matched paired audit. A direct native FAISS/cuVS invocation
outside \pkg{faissR} was not completed, so the article does not quantify
conversion, metadata, wrapping, or transfer overhead against a native caller.

Calibration retained timeout and out-of-memory failures as negative evidence,
but the completed campaign did not measure a valid isolated-process peak for
every candidate or provider index size systematically. Quantitative memory
comparisons are therefore omitted. Likewise, the three requested recall tiers
summarize calibrated operating points rather than full recall--time frontiers;
the prespecified Pareto and isolated-memory protocols in the supplement require
their dedicated runs before curves or memory claims enter the article.

These limits motivate conservative use: inspect \code{auto\_selection} and
\code{approximation} metadata, validate recall against an exact subsample when
the application is sensitive, and fit a persistent index when queries repeat.

\section{Discussion and conclusion} \label{sec:conclusion}

\pkg{faissR} provides a single nearest-neighbor interface across CPU and
NVIDIA GPU providers while preserving the distinctions that matter for
statistical computing: metric semantics, exact versus approximate evidence,
data representation, backend identity, and result residency. Requested-recall-
tier policies make the speed--accuracy choice visible rather than
embedding it in undocumented defaults. The optional experimental CUDA policy
extends this evidence to a narrowly scoped method-family convenience, but is
not a central performance claim of the package.

The evaluation supports three conclusions. First, route and metric semantics,
including the documented backend-dependent handling of undefined normalized
rows, are explicit and contract-tested across the evaluated CPU and CUDA paths.
Second, many approximate operating points do not reach ambitious recall tiers,
so negative calibration evidence is scientifically useful. Third, under the
evaluated cold full-self-search workload, the installed CUDA policy was
conservative and usually exact. Approximate selection produced substantial
gains in several large Euclidean cases but a large ImageNet penalty.
The post hoc cross-fitted sensitivity analysis had lower feasible-route regret
within its different candidate universe, but it does not validate or repair the
installed selector. Hardware-, workload-, and dataset-dependent exceptions
must remain visible; grouped domain holdout showed materially larger regret
than named-dataset LOODO. The package is
therefore best understood as auditable computational infrastructure, not as a
universal claim that one nearest-neighbor method dominates.
