\title{\pkg{faissR}: Recall-Aware CPU and GPU Nearest-Neighbor Search in \proglang{R}}
\Plaintitle{faissR: Recall-Aware CPU and GPU Nearest-Neighbor Search in R}
\Shorttitle{Recall-Aware Nearest-Neighbor Search in \proglang{R}}

\Abstract{
Nearest-neighbor search is a computational primitive for manifold learning,
retrieval, clustering, and supervised prediction. Existing \proglang{R}
interfaces cover individual algorithms, but accelerator-aware analyses also
require explicit device semantics, consistent metrics, float32 data flow,
reusable indexes, and auditable speed--recall choices.
\pkg{faissR} is an MIT-licensed, Python-free \proglang{R} package that requires
the FAISS \proglang{C++} library for CPU builds and optionally links to FAISS GPU,
NVIDIA CUDA, and RAPIDS cuVS. Its central \fct{nn} interface separates device
selection from algorithm selection and supports Euclidean, cosine, and
correlation search. Exact, inverted-file,
product-quantization, graph, and low-dimensional grid methods are exposed
through a common result contract. The package accepts optional \pkg{float}
matrices, reuses fitted indexes, performs batching and self-neighbor removal in
compiled code, and can return exact KNN buffers that remain on the GPU.
Deterministic compiled policies select parameters from dataset shape, neighbor
count, metric, backend, and a desired recall of 0.90, 0.95, or 0.99. This target
is an auditable calibration objective rather than a guarantee for a new
dataset. We describe the statistical contract, implementation, user interface,
calibration procedure, and a reproducible CPU/CUDA evaluation framework for
\pkg{faissR}.
}

\section[Introduction]{Introduction} \label{sec:introduction}

For a reference matrix $X \in \mathbb{R}^{n \times p}$ and a query matrix
$Q \in \mathbb{R}^{m \times p}$, nearest-neighbor search returns the $k$
reference rows most similar to each query row. The operation underlies
dimensionality reduction, local regression and classification, anomaly
detection, information retrieval, and many exploratory analyses of
high-throughput biological measurements. Exact self-search requires evaluation
of $O(n^2)$ pairwise scores, whereas approximate nearest-neighbor (ANN)
methods trade accuracy for lower search time, lower memory use, or both.

FAISS provides mature exact, inverted-file, product-quantization, and graph
indexes on CPUs and NVIDIA GPUs \citep{JohnsonDouzeJegou2021,DouzeEtAl2024}.
RAPIDS cuVS provides CUDA implementations of vector-search and clustering
primitives and is increasingly integrated with FAISS \citep{cuVS,FaissCuVS}.
Using these systems reproducibly from \proglang{R} nevertheless requires more
than forwarding a matrix to one library call. Base \proglang{R} matrices are
normally double precision and column-major, while FAISS and cuVS predominantly
consume float32 row-major data. Different providers expose different metric
and parameter conventions. Index construction can dominate repeated queries.
Finally, converting a GPU result into an ordinary \proglang{R} matrix implies
a device-to-host transfer that can erase the benefit of an otherwise fast
kernel.

The \pkg{faissR} package \citep{faissR} addresses these integration problems.
It is not presented as a new ANN algorithm. Its contribution is a unified,
auditable execution framework connecting \proglang{R} to FAISS CPU, optional
FAISS GPU, and optional direct CUDA/cuVS routes. The package adds metric-aware
float32 adapters, fitted-index reuse, compiled query batching and result
processing, GPU-resident output for downstream packages, and deterministic
parameter policies derived from recall-constrained calibration.

The article defines the common metric and metadata contract, distinguishes
\pkg{faissR}-owned code from FAISS and cuVS providers, formalizes the
recall-targeted calibration behind \code{tuning = "auto"}, and demonstrates
search, fitted-index reuse, float32 input, and GPU-resident interoperability.
Empirical claims concern nearest-neighbor search; secondary utilities such as
k-means are documented in the package reference manual.

\section{Nearest-neighbor problem and metric contract} \label{sec:metrics}

\subsection{Three public metrics}

Let $x_i$ and $q_j$ denote rows of $X$ and $Q$. The public metric names are
deliberately restricted to \method{euclidean}, \method{cosine}, and
\method{correlation}. Legacy aliases are rejected
so that benchmark and analysis scripts retain one canonical spelling.

Euclidean search minimizes the distance in Equation~\eqref{eq:euclidean},
%
\begin{equation} \label{eq:euclidean}
d_{\mathrm{E}}(q_j,x_i) = \left\|q_j-x_i\right\|_2.
\end{equation}
%
whereas cosine search minimizes Equation~\eqref{eq:cosine},
%
\begin{equation} \label{eq:cosine}
d_{\mathrm{cos}}(q_j,x_i) = 1 -
\frac{q_j^\top x_i}{\|q_j\|_2\|x_i\|_2},
\end{equation}
%
implemented by row normalization followed by equivalent normalized Euclidean
search. Correlation search is the centered cosine
distance in Equation~\eqref{eq:correlation},
%
\begin{equation} \label{eq:correlation}
d_{\mathrm{cor}}(q_j,x_i) = 1 -
\frac{(q_j-\bar q_j\mathbf{1})^\top(x_i-\bar x_i\mathbf{1})}
{\|q_j-\bar q_j\mathbf{1}\|_2\|x_i-\bar x_i\mathbf{1}\|_2}.
\end{equation}
%
Zero-norm cosine rows and constant correlation rows require explicit edge-case
semantics. \pkg{faissR} treats the corresponding normalized vector as zero and
uses deterministic exact handling where a provider cannot preserve the same
ties. An explicit CUDA call errors when correctness would otherwise require an
undisclosed CPU repair.

The frozen software evaluation includes deterministic conformance cases in
addition to empirical recall. Euclidean rankings are compared with a direct
squared-distance calculation. Cosine rankings must be invariant to positive
row scaling, and correlation rankings must be invariant to row-wise additive
shifts. Zero-norm cosine rows and constant correlation rows
are tested separately on CPU and CUDA. A provider route either reproduces the
documented edge-case contract or is recorded as unsupported; a different
metric or a CPU repair is not an acceptable substitute.

\subsection{Self-search, query search, and recall}

When \code{points} is omitted, \fct{nn} performs self-search. With
\code{exclude\_self = TRUE}, row $i$ is removed from its own candidate list in
compiled code. For a separate query matrix no row identity is assumed.

Approximate quality is measured against a metric-matched exact reference. For
query $j$, let $E_j(k)$ and $A_j(k)$ be the exact and approximate sets. Recall
at $k$ is given by Equation~\eqref{eq:recall},
%
\begin{equation} \label{eq:recall}
R_j(k)=\frac{|E_j(k)\cap A_j(k)|}{k}.
\end{equation}
%
For dataset $s$ and prespecified validation replicate $r$, let $Q_{s,r}$ be
the sampled query set and define the replicate-level statistic used for target
attainment as
\begin{equation} \label{eq:mean-query-recall}
\overline{R}_{s,r}(k;\theta)=
\frac{1}{|Q_{s,r}|}\sum_{j\in Q_{s,r}}R_{s,r,j}(k;\theta).
\end{equation}
Here $r$ denotes one prespecified validation-seed by timing-repeat pair, not a
dataset or a query. A dataset--method cell attains target $\tau$ only if every
prespecified replicate completes successfully and
$\overline{R}_{s,r}(k;\theta)\geq\tau$ for all $r$. Median and minimum
query-level recall are robustness diagnostics; minimum query recall is not the
target-attainment statistic.
Exact, Flat, and brute-force routes are mathematically exhaustive; their
tuning concerns batching, copying, and resource reuse rather than approximation
parameters. Set-based recall can nevertheless be slightly below one when an
exact provider chooses a different member of a tied boundary set, so the
benchmark records exactness separately from observed set overlap.

\section[Related software]{Related software} \label{sec:related}

The \proglang{R} ecosystem offers complementary nearest-neighbor interfaces.
\pkg{RANN} wraps ANN tree search \citep{RANN}; \pkg{Rnanoflann} exposes
nanoflann-based search \citep{Rnanoflann}; \pkg{RcppAnnoy} provides Annoy
indexes \citep{RcppAnnoy}; \pkg{RcppHNSW} exposes hnswlib HNSW indexes
\citep{RcppHNSW,MalkovYashunin2020}; and \pkg{rnndescent} implements
NN-descent-related methods \citep{rnndescent,DongMosesLi2011}.
\pkg{BiocNeighbors} provides a
common interface to multiple neighbor-search implementations used throughout
Bioconductor \citep{BiocNeighbors,Bioconductor}. \pkg{FNN} exposes kd-tree,
cover-tree, and exhaustive routes \citep{FNN}, while \pkg{nabor} wraps
low-dimensional libnabo search \citep{nabor}. Embedding packages such as
\pkg{uwot} also contain internal nearest-neighbor machinery, but their primary
public contribution is dimensionality reduction rather than a general
vector-search result contract.

These packages are not interchangeable: tree methods suit some
low-to-moderate-dimensional data, graph indexes favor repeated approximate
queries, and \pkg{BiocNeighbors} provides a stable Bioconductor abstraction.
\pkg{faissR} instead emphasizes the FAISS index family, explicit CUDA/cuVS
routes, float32 input, GPU-resident output, and a common recall-targeted policy.
The full comparator-by-metric eligibility table is provided in the supplement;
only packages exposing a comparable public KNN result are timed.

The relationship to FAISS and cuVS is also explicit. FAISS and cuVS retain
their own implementations and licenses; they are linked as system libraries
and are not copied into \pkg{faissR}. Native \pkg{faissR} code supplies
adapters, result shaping, auto-selection, low-dimensional grid search, and
selected candidate-graph construction/refinement routes. Provider metadata is
returned so that users can distinguish a FAISS GPU index from a direct cuVS
index rather than treating every CUDA result as the same implementation.
The package is MIT licensed. Its minimal adaptation of the public DLPack C ABI
retains the upstream copyright and Apache License 2.0 notice; FAISS and NVIDIA
libraries remain external dependencies and are not relicensed or vendored.

HNSW follows the hierarchical navigable small-world method
\citep{MalkovYashunin2020}; IVF-PQ follows product quantization
\citep{JegouDouzeSchmid2011}; NN-descent follows iterative neighbor-graph
refinement \citep{DongMosesLi2011}; NSG and Vamana-style refinement draw on
the NSG and DiskANN literature \citep{FuEtAl2019,SubramanyaEtAl2019}; and CAGRA
is supplied by FAISS GPU or cuVS. FAISS FastScan uses compact codes and SIMD
lookup-table accumulation \citep{FaissFastScan}. \pkg{faissR} acknowledges
these sources without claiming their algorithms as package inventions.

The preferred public spellings \method{nndescent\_style},
\method{nsg\_style}, and \method{vamana\_style} deliberately distinguish the
package-owned routes from feature-complete reproductions of the named reference
systems. The shorter historical spellings \method{nndescent}, \method{nsg},
and \method{vamana} remain compatibility aliases. Results record the stable
family identifier, the preferred public spelling, an implementation label and
scope, and whether the route is a canonical reimplementation. Printed
package-owned results state ``canonical reproduction: no.'' Direct cuVS
NN-descent is instead labelled as an external-provider implementation.

\subsection{Compiled data path and failure semantics}

The compiled core consumes contiguous float32 views. Base \proglang{R}
matrices are converted once; optional \pkg{float} matrices \citep{float}
avoid the double-to-float conversion, although a provider-specific layout
conversion may remain. Cosine normalization and correlation centering are
performed in compiled code and compatible transformed data are cached. The
default result uses ordinary numeric distances, while \code{output = "float"}
retains float32 distances on supported routes.

HNSW, IVF, IVF-PQ, and FastScan indexes can be reused by fitted \fct{knn}
models and compatible repeated \fct{nn} calls. Queries are batched, results
are returned already ordered, and self-neighbor removal occurs in compiled
code. These choices reduce conversion, construction, and \proglang{R}-side
post-processing overhead rather than changing the underlying search
mathematics.

The native NN-descent-, NSG-, and Vamana-style routes use fixed-width candidate
graphs with distinct refinement and pruning rules; their detailed algorithms
and complexity bounds are given in the supplement. They are not claimed to be
feature-identical reproductions of the reference systems. Every provider call
is checked against the requested backend, method, metric, and result shape. An
unsupported CUDA route therefore fails explicitly instead of executing on CPU.

\subsection{GPU-resident results and inter-package API}

Ordinary \fct{nn} results are host-resident. In contrast, \fct{nn\_gpu} returns
a \class{faissR\_gpu\_knn} object that owns CUDA index and distance buffers and
reports \code{result\_residency = "cuda"} and
\code{device\_to\_host\_result\_copies = 0}. The companion
\fct{gpu\_knn\_to\_host} makes the otherwise hidden transfer explicit.

The current GPU-resident ABI covers \method{auto}, \method{exact},
\method{flat}, and \method{bruteforce}, all resolving to exact-family device
buffers. Higher-dimensional Euclidean searches use FAISS GPU brute force when
available. For 2D/3D Euclidean data, direct CUDA
coordinate differences avoid float32 cancellation in the algebraically
equivalent norm/dot-product L2 identity. The installed header
\path{faissR\_api.h} declares typed callable
getters and an ABI-version query. Downstream packages list \pkg{faissR} in
\code{LinkingTo}, verify that \code{faissR\_c\_api\_version()} returns one, and
retrieve the registered entry point
\begin{Code}
faissR_nn_cuda_tuned_gpu_call
\end{Code}
without repeating its function-pointer signature. This
allows a CUDA-enabled embedding package to consume
indices and distances without converting them through an ordinary
\proglang{R} matrix. Ownership remains with the external pointer, preventing
two packages from freeing the same CUDA allocation.

For \code{method = "auto"}, the resident ABI distinguishes the ordinary
automatic-policy recommendation from the route that actually produced the
device object. Fields \path{auto_preferred_backend} and
\path{auto_preferred_method} record the unconstrained recommendation;
\code{method}, \path{backend_used}, and \path{execution_tuning} record the
executed route. The field \path{auto_residency_constraint} is
\code{"gpu\_resident\_output\_currently\_exact\_family\_only"} when an
approximate recommendation cannot yet be returned through this ABI. Thus
\fct{nn\_gpu} does not present the residency-constrained choice as the
unrestricted \fct{nn} policy.

\section{Recall-constrained automatic tuning} \label{sec:tuning}

\subsection{Optimization objective}

Useful ANN parameters depend on the number of rows $n$, dimension $p$,
neighbor count $k$, metric $d$, provider $b$, hardware $h$, and requested
quality. For method $a$, let $\Theta_{a,b,d}$ be a structured parameter grid.
For a desired operating point $\tau \in \{0.90,0.95,0.99\}$, calibration uses
the constrained objective in Equation~\eqref{eq:tuning}:
%
\begin{equation} \label{eq:tuning}
\theta^* = \mathop{\mathrm{arg\,min}}_{\theta \in \Theta_{a,b,d}}
\operatorname{median}_{s\in\mathcal{S}_g,\,r\in\mathcal{R}_s} T_{s,r}(\theta)
\quad\text{subject to}\quad
\min_{s\in\mathcal{S}_g}\min_{r\in\mathcal{R}_s}
\overline{R}_{s,r}(k;\theta) \geq \tau,\qquad F_{s,r}(\theta)=0,
\end{equation}
%
where $\mathcal{S}_g$ is the set of calibration datasets represented in shape
group $g$, $\mathcal{R}_s$ is the prespecified replicate set for dataset $s$,
$T_{s,r}$ is elapsed time, and $F_{s,r}$ indicates a failure, timeout,
unavailable backend, or route mismatch. The recall constraint uses the mean
query-level recall from Equation~\eqref{eq:mean-query-recall} and must hold for
every represented dataset and every complete replicate. If no setting reaches the
target, the calibration output retains the best available row but marks
\code{tuning\_benchmark\_target\_met = FALSE}; it is not silently promoted to a
validated target tier.

Within the feasible set, candidates are ordered by elapsed time, then higher
recall, then the lexicographic candidate identifier. If the feasible set is
empty, the order is higher recall, elapsed time, then candidate identifier.
Candidate identifiers are written before execution, making the choice
deterministic even when rounded times and recall values are identical.

Consequently, \code{target\_recall} is not a statistical guarantee. For an
explicit approximate method it requests the corresponding calibrated operating
point. If no complete candidate met the constraint, execution may use the best
complete-coverage candidate while reporting
\code{tuning\_benchmark\_target\_met = FALSE}. Applications that require a
guaranteed exact answer should request \method{exact} or reject any result whose
metadata does not document an acceptable evidence tier.

The default \code{tuning = "auto"} does not run a pilot benchmark. It calls
compiled \proglang{C++} selectors that map $(n,p,k,d,\tau)$ and runtime
capabilities to a method and parameter record. The default target is 0.99.
Pilot or cache-based tuning remains opt-in where implemented. Because the
static selectors summarize finite calibration data, the requested operating
point and the observed recall are reported separately throughout the article.

The selector is a deterministic interpolation policy, not a fitted model with
an unrestricted domain. Each policy record therefore carries the calibrated
shape group, metric, provider family, hardware provenance, and evidence tier.
Shape/capability cases outside implemented regimes use an exact route when the
compiled decision table defines one or fail explicitly. A hardware mismatch is
handled differently: it does not change the selected method, but returns
\code{hardware\_extrapolated\_unvalidated} evidence metadata. The article makes
no claim that two datasets with the same $(n,p)$ have the same neighbor
geometry or that calibration transfers unchanged between processor models.

\subsection{Calibration evidence}

Only candidates completing every dataset in a shape group are eligible for a
compiled policy. When none reaches the desired recall, the best complete
candidate remains available but carries
\code{tuning\_benchmark\_target\_met = FALSE}; partial or failed rows are never
promoted. The supplement reports candidate counts, target attainment, and
negative evidence separately for each method, metric, backend, $k$, and shape
group.

\subsection{Automatic method selection}

Method selection and parameter selection are distinct. Parameter selectors
choose $\theta$ within a requested method. The method selector applies a
compiled rule using shape, $k$, metric, desired recall, and backend.
Low-dimensional grid search is considered only for large 2D/3D self-search.
Exact search is favored when exhaustive work is cheaper than index construction
or when no approximate route has sufficiently strong calibration evidence for
the requested metric.
IVF is considered when coarse partitioning amortizes its build cost. Graph
methods are considered for repeated or sufficiently large high-dimensional
self-search where their calibration evidence supports the intended use.

The policy is conservative across metrics. A method is not selected for a
metric merely because it performed well for Euclidean distance. Proxy or seeded
rows are labeled and are not treated as metric-specific calibration evidence.
Returned metadata includes the rule identifier and whether the requested
operating point was reached in calibration. Section~\ref{sec:evaluation}
evaluates this selector against the fastest independently requested qualifying
method; it does not treat the selector's own prediction as validation.

The primary selector assessment is within the calibrated dataset collection.
A cross-fitted leave-one-dataset-out (LOODO) sensitivity analysis is defined
separately. For held-out dataset $s$, every calibration and selection row from
$s$ is removed before a method family is chosen from the remaining datasets
using only backend, metric, $k$, $\tau$, shape group, and distance in
$\log_{10}(n)$--$\log_{10}(p)$ space. The resulting family is then evaluated
on $s$ without revision from its timings or recall. This analysis measures
sensitivity to dataset identity but cannot establish out-of-collection
generalization. The selector is therefore described as a
calibration-informed operating-point policy, not as a dataset-independent
recall guarantee.

\subsection{A practical CPU workflow: letter recognition}

The UCI Letter Recognition data contain 20,000 distorted letter images from
20 fonts, represented by 16 numerical moments and edge-count features
\citep{FreySlate1991,mlbench}. This moderately sized public dataset makes the
speed--recall and index-reuse contracts visible without requiring a GPU. We
use the conventional first 16,000 observations for training and the remaining
4,000 for testing, estimating standardization parameters from the training
partition only.
%
\begin{CodeChunk}
\begin{CodeInput}

R> data("LetterRecognition", package = "mlbench")
R> y <- LetterRecognition$lettr
R> x0 <- as.matrix(LetterRecognition[, -1L])
R> train <- seq_len(16000L); test <- 16001:20000
R> center <- colMeans(x0[train, , drop = FALSE])
R> spread <- apply(x0[train, , drop = FALSE], 2L, sd)
R> x <- sweep(sweep(x0, 2L, center, "-"), 2L, spread, "/")
R> storage.mode(x) <- "double"
\end{CodeInput}
\end{CodeChunk}

First, exhaustive CPU search supplies the observed-reference neighborhoods.
The helper below computes mean query-level recall@15 by set overlap; this is
the same recall statistic used for a benchmark replicate, although the
single local run is an illustration rather than calibration evidence.
%
\begin{CodeChunk}
\begin{CodeInput}
R> recall_at_k <- function(reference, candidate) {
+    mean(vapply(seq_len(nrow(reference)), function(i) {
+      length(intersect(reference[i, ], candidate[i, ])) /
+        ncol(reference)
+    }, numeric(1)))
+  }
R> exact_time <- system.time({
+    exact <- nn(x, k = 15, exclude_self = TRUE,
+      backend = "cpu", method = "exact",
+      metric = "euclidean", n_threads = 4)
+  })[["elapsed"]]
\end{CodeInput}
\end{CodeChunk}

We then request three calibration-informed operating points. Each result keeps
the selected route, compiled tuning evidence, and runtime-hardware evidence;
no method identity is inferred from elapsed time.
%
\begin{CodeChunk}
\begin{CodeInput}
R> run_auto <- function(tau) {
+    elapsed <- system.time({
+      ans <- nn(x, k = 15, exclude_self = TRUE,
+        backend = "cpu", method = "auto", metric = "euclidean",

\subsection{Calibration and independent query-subsample validation}

Calibration and publication evaluation are separated. Calibration uses seed 4
to search method-specific grids. Validation uses seeds 20260706 and 20260807
to choose independent exact-reference query subsets and never reselects
parameters from validation timings. These seeds provide query-subsample
validation within the same named datasets; they are not described as evidence
of generalization to unseen datasets. Exact
references are generated at $k=100$ for samples of up to 1,024 queries; smaller
$k$ values are obtained by cropping the same ordered reference. The CUDA exact
reference pipeline saves a result only after an independent CPU FAISS Flat
audit passes. Three metric-specific Slurm jobs generate the real-data
references, while a fourth generates the spatial and norm-stress synthetic
references. This guards against a fast but incorrect GPU reference and permits
one failed metric job to be rerun without replacing valid references.

The calibration and validation workflow separates the two stages. The
publication benchmark evaluates $k\in\{15,30,50,100\}$, all three metrics,
and recall targets 0.90, 0.95, and 0.99. Each successful timing is repeated
three times for each of two fixed validation query-subset seeds, yielding six
prespecified replicates per cell. Target attainment requires the mean
query-level recall@k to meet the requested tier in every one of those six
replicates; minimum query recall is diagnostic only. Timings are summarized by
median and interquartile range. A method--data
combination has a 2,000-second timeout. CPU and CUDA jobs are separate; CPU
jobs use 12 allocated tasks and GPU jobs use one NVIDIA L40S with two CPU
tasks. Both execute in a frozen Singularity container \citep{Singularity}.

The wide calibration grids create a risk of selecting a candidate whose
apparent timing advantage partly reflects selection noise. We therefore
prespecify a descriptive stability audit on the independent validation runs.
Within every dataset--backend--metric--$k$--target cell and each validation
seed--repeat pair, the audit reconstructs the fastest eligible explicit
\pkg{faissR} route. Exhaustive aliases resolving to the same provider are
collapsed into one exact-route family. The reported quantities are the modal
oracle-route frequency, route-switch frequency, number of distinct oracle
routes, \method{auto}/oracle route agreement, validation target-retention
frequency, timing coefficient of variation, and the validation
\method{auto}/oracle time ratio. A stable operating point has one oracle route
across all six prespecified replicates; lower modal frequency exposes ranking
sensitivity directly. The wide grids themselves were not independently
refitted, so this audit estimates route-selection stability under independent
query and timing repetitions, not a configuration-level reselection
probability.

The installed selector does not benchmark or fingerprint-match the runtime
against this table. On any capability-compatible machine it applies the same
compiled shape/metric/$k$/target policy. A confirmed NVIDIA L40S model match is
labelled \code{calibration\_hardware\_matched}; a different or unidentified
device is labelled \code{hardware\_extrapolated\_unvalidated}. The latter does
not assert that the route is locally fastest or that its approximate-recall
operating point has transferred. No exact or CPU fallback is triggered solely
by a hardware model mismatch, because such a fallback could silently change
the requested computational contract and model strings alone do not establish
performance equivalence. Users can request \code{method = "exact"} explicitly
or perform local recalibration.

CUDA elapsed regions are closed only after an explicit provider/device
synchronization. Cold timing includes metric transformation, host-to-device
transfer, training, index construction, search, and result creation. Warm
timing reuses a fitted index and transformed data where the public API permits
it. Device-to-host materialization is timed separately for GPU-resident
results. The archive records both the requested allocation and the effective
thread count reported by each implementation.

No unreported warm-up call precedes a cold measurement: first-call provider
initialization is therefore part of the user-visible cold time. Warm results
are labeled separately and are never substituted for cold results. Elapsed
time is measured around the complete public call with
\code{proc.time()[["elapsed"]]}, and each successful cell is repeated three
times. The Slurm allocation is a resource ceiling; the effective-thread field,
rather than the requested task count, is used when interpreting parallel
scaling.

The dataset, rather than an individual query, is the primary unit for
cross-method conclusions. Repeated timings quantify run-to-run variation on a
fixed dataset and are summarized by median and interquartile range. Query-level
mean, median, and minimum recall describe within-dataset quality, while
dataset-level completion and target-attainment proportions summarize
robustness. No inferential claim treats thousands of neighbor rows from one
dataset as independent experimental replicates. Generalization of the compiled
shape rules beyond the benchmark collection remains a limitation.

The LOODO sensitivity analysis uses the dataset as the held-out unit. For each
metric, backend, $k$, and target, policy rows are rebuilt without one named
dataset and then applied to that dataset without revision. A cross-fitted
operating point is attained when the selected held-out route completes all
replicates and is either exact-audited or, for an approximate route, reaches
$\overline{R}_{s,r}(k) \geq \tau$ in every prespecified validation replicate.
For each held-out dataset we report the attainment frequency, selected/oracle
cold-time ratio, route-family agreement with the fastest eligible explicit
method, abstention frequency, and exact-selection frequency. Exact selections
are not counted as approximate target-attainment events. The installed
\method{auto} result is also summarized as a non-independent diagnostic, but
it is not labeled LOODO evidence because its compiled policy used the full
calibration collection. Both summaries are separate from query-subsample
validation.

\subsection{Comparators and outcomes}

All applicable \pkg{faissR} methods in Table~\ref{tab:methods} are tested
individually, including \method{auto}. CPU comparisons include
\pkg{Rnanoflann}, \pkg{RANN} kd- and bd-tree routes, and \pkg{RcppAnnoy}
Euclidean and angular-cosine routes,
\pkg{RcppHNSW}, four \pkg{rnndescent} routes, and exhaustive, HNSW, and Annoy routes available
through \pkg{BiocNeighbors}. \pkg{FNN} kd-tree, cover-tree, and brute-force
routes and \pkg{nabor} automatic and brute-force routes are also included.
The frozen \pkg{uwot} build is retained in the API audit, but it does not
export a standalone nearest-neighbor result interface; namespace internals and
embedding runtime are therefore not timed as KNN search. We also audited
\pkg{cuda.ml}, but its current public
\fct{cuda\_ml\_knn} interface requires supervised outcomes and returns a
prediction model rather than self-KNN index and distance matrices
\citep{cudaML}; the campaign therefore records it as non-standalone instead of
timing a non-equivalent task. Embedding functions from t-SNE or UMAP packages
are likewise not reported as standalone nearest-neighbor algorithms unless
they expose a comparable KNN result.

Comparators are admitted only when their public interface can express the same
metric, self-exclusion convention, and requested $k$. CPU methods receive the
same 12-task allocation, although a package that is intrinsically single
threaded is not represented as using 12 effective workers. CUDA and CPU
rankings are never pooled. Cold end-to-end time includes transformations,
training, index construction, search, and result materialization; warm query
time is reported only for interfaces that expose a reusable fitted object.
The primary cold comparison requests neighbors for all rows. The separate
reusable-index diagnostic builds once and queries the independently sampled
exact-reference rows (at most 1,024) so that construction, first sampled query,
and three repeated sampled queries are identifiable without presenting the
warm subset timing as a full all-row timing.
The evaluation answers two distinct performance questions.
\paragraph{End-to-end user-visible API performance.}
The primary package comparison uses the input representation accepted by each
public interface and times the complete public call. It therefore estimates
what an \proglang{R} user experiences, including conversion, layout,
construction, search, and materialization. It is not interpreted as a pure
algorithmic comparison.
\paragraph{Search/index performance conditional on compatible representation.}
The systems ablation fixes float32 input, metric, $k$, backend, and output
contract before comparing routes. Within a fixed route and phase, the
representation ratio is
$Q_{\mathrm{repr}}=T_{\mathrm{float32}}/T_{\mathrm{double}}$. Within a fixed
float32 route, the reuse ratio is
$Q_{\mathrm{reuse}}=T_{\mathrm{warm}}/T_{\mathrm{cold}}$. Finally,
$Q_{m/\mathrm{Flat}}=T_{m,\mathrm{float32}}/
T_{\mathrm{Flat},\mathrm{float32}}$ compares a provider/search route with Flat
while cache use is disabled in both arms. Ratios below one favor the numerator.
The last contrast includes the provider's index construction, search, and
result creation; it is conditional route performance, not a kernel-only or
implementation-independent statement about the mathematical algorithm.

Comparative timing effects are paired within identical dataset, metric, $k$,
target-recall, backend, and validation designs. The primary package comparison
uses the frozen \method{auto} policy rather than retrospectively choosing the
fastest \pkg{faissR} route. For each comparator, valid cell ratios are reduced
to a median within each dataset; cross-dataset summaries then use those
dataset-level medians as equally weighted observations. We report the median,
IQR, and range of dataset ratios together with expected and paired
dataset/cell counts, unpaired cells, timeouts, and out-of-memory events.
Absolute elapsed times are descriptive supplementary outcomes rather than
cross-cell effect estimates.

Each raw benchmark row freezes the exact public call, package version,
allocated threads, requested threads, and threading scope for its comparator;
\code{sessionInfo()} supplies the wider software environment. A warm result is
reported only when that package exposes a public
build-once/query-many interface; packages without such an interface contribute
only a cold result. A warm fitted-index time is never compared with another
package's cold one-call time. For \pkg{RcppAnnoy}, the public item-query method
is called iteratively because the package does not expose a matrix-batch query;
this is recorded as interface behavior rather than described as batched
execution. Its angular distance $\sqrt{2-2\cos(x,y)}$ is converted inside the
timed adapter to the public cosine distance as $d_{\mathrm{angular}}^2/2$.
The four public \pkg{rnndescent} calls are evaluated under Euclidean, cosine,
and correlation metrics.
Before a stochastic external route is called, the worker initializes
R's RNG from the prespecified run seed; explicit package seed arguments are
also supplied where available. The resulting algorithm seed is retained in
the raw row. Repetition remains necessary because parallel graph construction
may not be bitwise deterministic under a fixed seed. For \pkg{RcppHNSW}, the campaign records both the complete
\fct{hnsw\_knn} call and a separate \fct{hnsw\_build}/\fct{hnsw\_search}
experiment, using the same $M$, construction effort, query effort, random seed,
and requested thread count in the recorded parameter string. If multiple
\pkg{faissR} names resolve to the same
exhaustive provider route, the aggregate retains their wrapper timings but
counts the provider once when ranking distinct algorithms.

Distance-error diagnostics use the public \pkg{faissR} scale rather than each
provider's incidental output units. In particular, \pkg{BiocNeighbors}
cosine routes return Euclidean distances between normalized vectors; the
benchmark converts them inside the timed adapter as
$d_{\mathrm{cos}}=d_{\mathrm{normalized\mbox{-}L2}^2}/2$. This conversion
does not affect neighbor order or recall, but makes distance error comparable
with the documented $1-\mathrm{cosine}$ contract. The exact call and
conversion are retained in the raw parameter string. After canonical unit
conversion, distance error is calculated only for neighbor identifiers shared
by the candidate and exact results, with positions matched by identifier rather
than by rank. Set recall separately penalizes missing exact neighbors. Thus, a
rank permutation of the same neighbors cannot create a spurious distance error,
and an incorrect neighbor is not compared with an unrelated exact distance.

Reported outcomes are cold end-to-end time, warm/repeated-query time, index
build time where separable, query time, recall at $k$,
minimum query recall, rank agreement, distance error, provider/route metadata,
timeouts and failures, and host--device copy counts and time. Exact-family
methods are classified as \emph{exact-audited}, separately from approximate
target attainment. The tie-aware criterion accepts a query when its identifiers
match the reference set or when its sorted distance multiset matches within
$10^{-5}+10^{-4}\max(|d|,|d_{\mathrm{ref}}|)$. Thus, an arbitrary member of a
tied $k$th-neighbor boundary cannot make an exhaustive route ineligible. Raw
set overlap remains a diagnostic. Elapsed time surrounds the complete public call and
is not presented as kernel-only time. The Linux
\path{/proc/self/status} \code{VmHWM} field is monotone over a process lifetime.
Because the performance and systems-ablation workers evaluate more than one
benchmark operation per R process, their row-level \code{VmHWM} values can
inherit an earlier peak and are excluded from quantitative host-memory
comparisons. The aggregators accept a host-memory value only when its raw row
explicitly records a fresh process dedicated to that single measured cell;
shared-worker rows are treated as unavailable. Consequently, this
study reports host out-of-memory events but makes no quantitative CPU peak-memory
claim from these measurements. \code{VmHWM} also does not measure CUDA device
allocation. Device-memory results must therefore come from explicit
CUDA/provider telemetry in the frozen archive or be reported as unavailable.
Sampled \code{nvidia-smi} process memory, when used, is labeled as an external
high-water estimate and not as an allocator-exact measurement.

For exact references, the primary quality endpoint is set recall on the sampled
queries. Identifier-matched distance error and rank agreement are retained as
sensitivity diagnostics because tied points at the $k$th boundary can produce
different but equally valid exact sets. Frozen legacy held-out rows without a
per-run tie-aware field are marked exact-audited only when their route is
exhaustive by construction and the corresponding frozen reference passed the
independent tie-aware CPU audit; the aggregation records this audit basis.
The final tables report the number of sampled queries
and do not extrapolate minimum sampled recall into a population guarantee.

\section{Results} \label{sec:results}

\subsection{Exact-reference validation}

The retained three-metric reference campaign contains 87 metric-matched
objects: 81 real-data cells (27 for each metric) and six 2D/3D Euclidean
spatial cells. All objects completed successfully and passed
an independent tie-aware CPU FAISS Flat audit. The audit accepted either
identical neighbor identifiers or an equivalent sorted distance multiset at
the frozen absolute and relative tolerances. Across objects, mean sampled-query recall
was 0.99986 and the minimum sampled-query recall was 0.99. Every object
recorded \pkg{faissR} 0.99.21 and identical package and image commit
\code{0903532baf02b340a90921db18edc4deae5ea462}.

This run also exposed and corrected an artifact-design issue before timing:
synthetic datasets shared one directory while the original reference filename
did not contain dataset identity. The revised builder prefixes every synthetic
reference with the dataset filename and the audit requires one unique path per
dataset--metric--seed cell. Earlier colliding synthetic files are excluded.
Earlier reference objects that predated mandatory package/image commit fields
remain excluded. The regenerated 150-object set satisfies the version, commit,
identity, existence, status, and CPU-audit gates used by the campaign.

\subsection{Calibration-policy outcome}

The calibration audit retains only Euclidean, cosine, and correlation rows.
Its target-attainment and missing-cell counts are reported by backend, method,
metric, $k$, and target in the supplement. These proportions summarize
individual method-policy cells, not the performance of \method{auto}.
Importing only complete, target-meeting coverage prevents a fast result from
one dataset from standing in for failed or absent datasets in the same policy
group.

\subsection{Correctness and recall-target compliance}

The pre-freeze deterministic conformance suite used a non-degenerate
$1024\times19$ float32 fixture with $k=15$ and desired recall 0.99. On CPU,
all 35 supported method--metric cells passed dimensions, finite-distance,
ascending-distance, resolved-route, and metric-invariance checks. All 22
zero-norm cosine or constant-row correlation cells also passed. On CUDA,
all 38 supported cells passed the metric contract. All 24 CUDA degenerate-row
cells followed the documented
finite-result or explicit no-CPU-repair behavior.

Metric conformance does not imply that an approximate index attained the
requested recall. On this fixture, 27 of 35 CPU cells and 32 of 38 evaluated
CUDA cells reached 0.99 recall. CPU misses were confined to IVF under cosine
or correlation and to IVF-PQ/FastScan variants. CUDA misses were confined to
IVF-PQ and IVF-PQ FastScan. These fixture-level results establish interface
contracts, not dataset-level performance.

\subsection{Comparative performance}

Performance comparisons are paired within an identical dataset, metric, $k$,
desired-recall, backend, validation-seed, and timing-repeat design. For an
external comparator $c$, the primary cell-level effect is
\begin{equation}
S_{d m k \tau c} =
\frac{T_{d m k \tau c}}{T_{d m k \tau,\mathrm{auto}}},
\end{equation}
where values above one favor \pkg{faissR} automatic selection. Selector regret
uses the converse interpretation,
\begin{equation}
G_{d m k \tau} =
\frac{T_{d m k \tau,\mathrm{auto}}}
     {T_{d m k \tau,\mathrm{oracle}}},
\end{equation}
where values above one favor the empirical oracle. Ratios are calculated only
after each arm's six-run cell summary passes the frozen completeness and
quality rules.

The dataset is the primary unit. Cell ratios are first reduced to one median
ratio within each dataset and comparator; the reported cross-dataset estimate
is then the median of these dataset-level ratios, with IQR and full range.
Consequently, a dataset contributing many successful cells cannot dominate a
dataset contributing fewer cells. Reports also include the numbers of expected
and paired datasets and cells, unpaired cells, timeouts, and out-of-memory
events. Unpaired failures remain in completion denominators and are never
converted to favorable finite ratios. The frozen aggregation stage writes the
cell, dataset, and cross-dataset tables and
log2 paired-ratio plots. Absolute elapsed-time summaries are retained only in
the supplement as operational context.

The completed CUDA \method{auto} streams were eligible under their resolved
exact or approximate route in 100\% of cells. Their raw set-overlap diagnostic
was 99.1--100\%; the two correlation/cosine deficits and one Euclidean deficit
did not indicate an exhaustive-search failure. CPU HNSW reached its
approximate target in 94.4\% under correlation and 95.4\%
under cosine. External CPU comparisons were complete for Annoy, while
exhaustive and HNSW comparators recorded 48 per-cell timeouts each, confined to
the FlowRepository and ImageNet datasets. These failures are retained as
scalability evidence. The broader CPU method matrix and remaining CUDA routes
are still being completed; no overall fastest-method or auto-versus-oracle
claim is made from the heterogeneous absolute-time summaries.

\subsection{Automatic selection versus the empirical oracle}

The automatic selector is evaluated as a method in its own right. Within each
dataset, backend, metric, $k$, and desired recall cell, the empirical oracle is
the fastest explicitly requested \pkg{faissR} method that completed every
validation repeat and was either exact-audited or, for an approximate method,
met the recall threshold in every repeat. This is the
attainable oracle for a selector whose action space is limited to \pkg{faissR};
the overall cross-package winner is reported separately. The comparison reports the
auto/oracle time ratio, recall difference, resolved-provider agreement, and
whether automatic selection reached the desired operating point. Cells with no
qualifying explicit method are reported as unsupported evidence rather than
assigned an oracle retrospectively. This analysis tests the selector without
using validation timings to revise it.

Selection stability is reported alongside the aggregate oracle comparison,
not inferred from the single fastest calibration timing. The replicate table
records the eligible winner separately for each validation seed and repeat;
the cell table reports its modal frequency and switches; and the
backend--metric--target table summarizes complete cells with the dataset as
the unit. These outputs distinguish a consistently superior route from a
narrow winner whose rank changes under independent validation. They also
retain incomplete or failed cells in the completeness accounting. Numerical
stability claims are withheld until every explicit-method stream required to
construct the replicate-specific oracle is complete.

The cross-fitted LOODO analysis is the dataset-identity sensitivity test for
the selector. It reports results by omitted dataset as well as by backend,
metric, and target. Its primary quantities are operating-point attainment,
selected/oracle time ratio, route-family agreement, abstention frequency, and
exact-selection frequency. The selected/oracle ratio is defined only when the
cross-fitted selection is eligible and a held-out empirical oracle exists.
Accordingly, an abstention is not converted to an infinite ratio or silently
removed from the attainment denominator.

\subsection{Systems ablations}

Dedicated CPU and CUDA jobs isolate base double versus \pkg{float} input,

self-neighbor handling, and host-returned versus GPU-resident exact output on

conversion, construction, post-processing, and transfer overhead.

\section{Software quality and reproducibility} \label{sec:quality}

The MIT-licensed package has no Python dependency; FAISS, CUDA, and cuVS remain
external system libraries under their respective licenses. The repository
contains unit tests, API documentation, a vignette, feature-detecting build
scripts, and CPU/CUDA route tests. The benchmark evidence described here was
frozen with version 0.99.21 at commit
\code{0903532baf02b340a90921db18edc4deae5ea462}.

Benchmark jobs are generated from a manifest and test one method, backend, and
metric per launcher. They record failures rather than substituting another
route. Before loading data, every launcher checks both the package version and
the 40-character source commit embedded in the image; a same-version image from
a different commit is rejected. Every raw timed-result row and exact-reference
object carries the dataset fingerprint, package version, required package
commit, embedded image commit, route metadata, seed, repetition, and environment
record. Aggregation preserves these identity fields and the strict freeze audit
rejects missing, malformed, or unequal package/image commits. CUDA QA also
checks that GPU-resident results own device pointers and report zero
device-to-host result copies.

The compact replication entry point, \path{manuscript/jss/code.R}, delegates to
\path{replication_article.R} and runs small CPU examples on a regular computer.
Its executed \path{code.html} records the example summary and
\code{sessionInfo()}. Given the frozen result directory, the same entry point
also verifies schemas and fingerprints and regenerates article tables without
rerunning the HPC campaign. SHA-256 digests identify the package source,
container, distributed data, and frozen result archive. Detailed launcher,
eligibility, rerun-selection, and freeze rules are provided in the supplement.
The full special-hardware campaign has a single commented submission program,
\path{final_campaign/submit_campaign.R}. It validates the installed package
version and embedded source commit, then submits each existing CPU/CUDA Slurm
launcher separately for one explicitly requested phase. It records a CSV job
ledger and never advances to a later phase automatically, so report inspection
and policy-freeze gates remain enforceable. The ledger is persisted after every
\code{sbatch} call, preserving accepted job identifiers even when a later
submission in the same phase fails.

\section{Limitations} \label{sec:limitations}

First, performance policies are conditional on hardware and provider versions.
A rule calibrated on one CPU or NVIDIA GPU generation is a reproducible default,
not a universal optimum. It interpolates among observed shape regimes and does
not imply that datasets with equal dimensions have equal search geometry.
The current implementation retains that policy on capability-compatible but
unmatched hardware and labels the result
\code{hardware\_extrapolated\_unvalidated}; it does not claim local optimality
or silently change methods. Metadata and calibration scripts are therefore part
of the contribution, and future releases should periodically recalibrate. A
second CPU/GPU platform would strengthen portability evidence but is not used
to support the present hardware-conditional claims.

The desired \code{target\_recall} is a calibration objective, not a guarantee
for a new dataset. Below-target and proxy-derived policies remain executable
only with explicit negative evidence metadata. The independent validation seeds
resample queries within the benchmark datasets and therefore do not establish
out-of-collection generalization of the shape rules.

Second, not every method supports every backend, metric, query mode, or data
shape. In particular, CAGRA is CUDA-only, grid search is restricted to 2D/3D
self-search, and the current GPU-resident ABI is exact-family only. CUDA HNSW
uses cuVS HNSW constructed from a CAGRA graph and should not be described as a
pure all-GPU HNSW search path.

Third, source installation requires FAISS headers and libraries. CPU-only
users do not need NVIDIA software, but GPU builds require a compatible CUDA,
FAISS GPU, and/or cuVS toolchain. The current package metadata targets Unix-like
systems; Windows support and binary distribution require additional work.

Fourth, transformed metrics have edge cases. Cosine zero vectors and constant
rows under correlation require explicit semantics and metric-matched
references. Approximate recall for one metric
cannot be transferred to another without validation.

Fifth, the empirical campaign evaluates nearest-neighbor search rather than
every exported utility. The Letter Recognition example demonstrates fitted
\fct{knn}/\fct{predict} behavior, batched prediction, reuse, and observed
accuracy, but it is not a comparative classifier study. \fct{fast\_kmeans} is
documented as a secondary utility; clustering quality, convergence behavior,
and CPU/CUDA k-means performance are not evaluated here and no corresponding
empirical claim is made.

Exact-reference recall is evaluated on at most 1,024 sampled queries per
dataset. This supports practical comparisons on million-row data but does not
establish a worst-case guarantee over every query. Minimum sampled recall,
distance error, rank agreement, and the sampled-query count must therefore be
interpreted together.

Finally, \pkg{faissR} exposes several algorithms but does not make them
mathematically equivalent. The convenience of \method{auto} should not replace
inspection of exactness, recall evidence, provider metadata, memory, and build
cost for high-stakes analyses.

\section{Discussion and conclusion} \label{sec:discussion}

\pkg{faissR} brings a broad FAISS and CUDA/cuVS vector-search surface into
\proglang{R} while retaining explicit statistical and systems contracts. The
package separates backend from method, reports the route actually executed,
uses a canonical three-metric interface, and treats failure as data rather than
an invitation to silently change algorithms. Float32 adapters, transformed-data
caching, persistent indexes, compiled post-processing, batched queries, and
GPU-resident outputs address overheads that are often hidden by algorithm-only
benchmarks.

The principal methodological software contribution is recall-aware automatic
tuning. Parameters are selected by constrained optimization on calibration
data. The frozen evaluation protocol then assesses them on independent query
subsamples without revising the policy. Shape, $k$, metric, backend, and
desired recall enter compiled selectors, while below-target and proxy-derived
rules remain visible in metadata. The desired recall is not a guarantee, and
selector performance must be assessed against the fastest qualifying explicit
method rather than inferred from calibration. This design makes automatic
selection auditable and exposes regimes where exact search or additional
calibration is preferable.
