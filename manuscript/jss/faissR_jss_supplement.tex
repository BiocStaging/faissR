\section{Purpose and evidence boundary}

This supplement documents the software surface, benchmark design, metric
contracts, pre-freeze conformance runs, and systems-ablation coverage supporting
the accompanying Journal of Statistical Software manuscript. It deliberately
separates three kinds of evidence:
\begin{enumerate}
\item \textbf{Metric conformance}: whether a requested route preserves the
documented distance, ordering, shape, and backend contract.
\item \textbf{Exactness audit}: whether an exhaustive route returns the same
identifier set or an equivalent sorted distance multiset within the frozen
absolute and relative tolerances.
\item \textbf{Recall-target attainment}: whether an approximate route reaches
a requested operating point on a specified fixture or dataset.
\item \textbf{Comparative performance}: cold and warm elapsed time, memory, and
completion on held-out query subsets.
\end{enumerate}
An exact-family cell is selection-eligible after the exactness audit passes;
its set-overlap recall is diagnostic. An approximate cell is eligible only if
every prespecified replicate's mean query recall@k reaches the requested tier.
The empirical oracle uses the union of these two disjoint eligibility classes.
The supplement reports only evidence that passes the package-route,
exact-reference, calibration, and result-completeness audits. Coverage and
descriptive summaries are presented without claiming a universal method
ranking across hardware or data collections.

Canonical metric names are \method{euclidean}, \method{cosine}, and
\method{correlation}. Cosine uses row normalization and correlation uses row
centering followed by normalization. For cosine, a zero-norm row follows the documented
finite-result or explicit unsupported-path contract; for correlation, the same
rule applies to constant rows after centering. CUDA routes are not allowed to
repair either edge case by silently executing a CPU search.

The native candidate-graph routes share a fixed-width candidate matrix but use
different refinement rules. NN-descent joins forward and reverse candidates,
scores unique pairs, and retains the best candidates until convergence or the
iteration limit. NSG/MRNG-style refinement rejects candidate $y$ for vertex
$x$ when an already retained $z$ satisfies $d(z,y)<d(x,y)$. Vamana-style
refinement instead applies $\alpha d(z,y)\leq d(x,y)$ and protects the first
$k$ seed neighbors. Self edges and duplicates are removed and distance--index
ordering gives deterministic ties for a fixed seed and thread configuration.
If $g$ is seed width, $c$ candidate width, and $I$ the iteration count, storage
is $O(n(g+c))$ indices plus the input and worst-case fixed-width scoring is
$O(Incp)$. These are package-owned style implementations, not feature-complete
copies of the reference NSG, DiskANN/Vamana, or NN-descent systems.
The preferred public names are therefore \method{nsg\_style},
\method{vamana\_style}, and \method{nndescent\_style}. The shorter historical
names remain compatibility aliases. Each result exposes
\code{preferred\_public\_method}, \code{implementation\_label},
\code{implementation\_scope}, and \code{canonical\_reimplementation}; the
package-owned routes set the last field to \code{FALSE}. Direct cuVS
NN-descent is separately identified as an external-provider route.

\section{Tuning and validation design}

Method-specific tuning grids vary the parameters that control construction,
candidate breadth, compression, and search effort. The most important
families are:
\begin{itemize}
\item HNSW: graph degree $M$, construction effort, and query \code{efSearch};
\item IVF: \code{nlist} and \code{nprobe};
\item IVF-PQ/FastScan: \code{nlist}, \code{nprobe}, PQ dimensions/subquantizers,
code width, FastScan block size, and optional refinement;
\item CAGRA: provider, build algorithm, graph/intermediate degree, and search
width;
\item NN-descent: pool/candidate breadth, graph degree, random projections,
and iteration controls;
\item NSG/Vamana: seed-graph size, candidate pool, pruning degree, search
breadth, and Vamana $\alpha$;
\item exact/Flat/brute force: batch size, conversion/copy behavior, resource
reuse, and fitted-index reuse.
\end{itemize}

For each backend, metric, shape group, $k\in\{15,30,50,100\}$, and desired
recall in $\{0.90,0.95,0.99\}$, calibration selects the fastest successful
candidate meeting the threshold. If no candidate reaches the threshold, the
best available row is retained with explicit negative-evidence metadata rather
than relabeled as successful. Exact-family methods record exactness by
construction, must pass the exhaustive-route and tie-aware reference audit,
and tune only systems parameters. Their raw set-overlap recall does not enter
ANN target-attainment classification.

The threshold statistic is defined at the validation-replicate level. For
dataset $s$, replicate $r$ is one prespecified query-subset seed by timing-
repeat pair, and its statistic is mean query-level recall@k over that sampled
query set. Target $\tau$ is attained only when this mean is at least $\tau$ in
every complete replicate; a shape-group calibration row must satisfy the same
condition for every represented dataset. Median and minimum query-level recall
are robustness diagnostics, but minimum query recall is not the acceptance
threshold. CSV metadata names this statistic
\code{mean\_query\_recall\_at\_k} and the replicate rule
\code{all\_prespecified\_validation\_replicates}.

Calibration uses seed 4. Independent publication evaluation uses query subsets
from seeds 20260706 and 20260807; validation timings cannot alter the compiled
policy. Exact references are generated at $k=100$ for up to 1,024 queries and
cropped for smaller $k$. A CUDA reference is saved only after an independent
CPU FAISS Flat audit. Each successful validation timing is repeated three
times, and each method--dataset job has a 2,000-second timeout.

Because the grids are wide, the final aggregation includes a descriptive
selection-stability audit. For each validation seed--repeat pair it selects
the fastest successful explicit \pkg{faissR} route that is exact-audited or
meets the requested recall in that replicate. Exact, Flat, brute-force, and
grid aliases resolving to the same exhaustive provider are collapsed to an
exact-route family before ranking. For each dataset--backend--metric--$k$--
target cell, the audit writes the number of distinct winning routes, modal
winner and modal fraction, switch fraction, deterministic \method{auto}-route
fraction, \method{auto}/oracle agreement, target-retention fraction, timing
coefficient of variation, and median and interquartile
\method{auto}/oracle timing ratios. Backend--metric--target summaries use
complete cells only. This is an independent-validation ranking-stability
analysis; the calibration grids were not independently refitted, and the
reported frequencies must not be described as parameter-level reselection
probabilities.

\section{Hardware-policy interpretation}

The compiled automatic selector is a frozen policy, not an online hardware
optimizer. Its calibration profile identifier is
\code{uct\_hpc\_cpu12\_nvidia\_l40s\_2026}. Runtime capability checks can
exclude unavailable providers, but a processor-model mismatch does not change
the selected method. The auto-selection record reports the calibration and
runtime model strings, \code{hardware\_match\_status},
\code{hardware\_evidence}, and
\code{hardware\_policy\_action}. Any status other than a confirmed match is
classified as \code{hardware\_extrapolated\_unvalidated}. This classification
limits performance and approximate-recall claims; it does not imply an
execution failure or an exactness failure.

The frozen QA identified the NVIDIA L40S accelerator and driver, but did not
capture a unique physical CPU model, installed host RAM, compiler build string,
or exact FAISS/CUDA/cuVS versions. Those omissions are retained as explicit
provenance gaps. Future campaign QA must write these values before timing; they
must not be reconstructed from node names or inferred from feature
availability.

The datasets are COIL20 and MNIST at $k=30$ under Euclidean
distance. CUDA timings synchronize provider/device work before returning.
The ablation answers two questions that are kept separate from the external
package comparison. End-to-end user-visible API performance permits each public
interface's accepted representation and includes every operation inside the
public call. Conditional search/index performance fixes a compatible float32
representation before route comparison. Three primary ratios are emitted:
\code{float32\_over\_double} at fixed route and cache-disabled phase,
\code{warm\_over\_cold} at fixed route with float32 input, and
\code{route\_over\_flat} with float32 input and caching disabled in both arms.
The latter includes index construction and result creation and is therefore a
provider-route contrast rather than a kernel-only algorithm comparison.

The aggregator preserves the conditioning phase in
\path{jss_ablation_float32_contrasts.csv} and the conditioning input type in
\path{jss_ablation_cache_contrasts.csv}. It additionally writes
\path{jss_ablation_route_over_flat_contrasts.csv} and
\path{jss_ablation_component_summary.csv}. Before cross-dataset summarization,
cell ratios are reduced to one median per dataset so datasets, rather than
methods or timing repetitions, receive equal weight. Ratios below one favor
float32, warm reuse, or the named route, respectively.

The host \code{VmHWM} observations in these runs are process-lifetime high-water
marks from workers that executed multiple operations. They are retained for
provenance but are marked invalid for per-cell quantitative comparison; the
aggregator emits host-memory medians and ratios only for rows carrying an
explicit fresh-process-per-measurement validity flag. No current systems-ablation
row meets that criterion, so host-memory effect estimates are intentionally
absent and out-of-memory events are reported as outcomes instead. Sampled
\code{nvidia-smi} process memory is separate from host RSS and is labeled as an
external high-water estimate rather than allocator-exact telemetry. The
completed row counts establish that the intended timing arms executed. In the
pre-freeze archive, the dataset-first median float32/double ratios were 0.746
on CPU and 0.798 on CUDA; warm/cold float32 ratios were 0.822 and 1.002,
respectively. Conditional route/Flat ratios varied sharply by dataset: CPU
HNSW ranged from 0.489 to 1.031, while CUDA CAGRA ranged from 0.952 to 43.98.
These values are engineering diagnostics, not final frozen effects. Final
numerical estimates require package-, image-, and fingerprint-matched pairing;
medians pooled directly across methods, shapes, or timing repetitions are not
valid ablation effects.

\section{External comparison plan}

Absolute elapsed times are retained as reproducibility metadata, but they are
not the primary comparative estimand. The publication aggregator writes
\path{jss_paired_performance_cells.csv},
\path{jss_paired_performance_by_dataset.csv}, and
\path{jss_paired_performance_summary.csv}. The first table preserves every
expected pair and its failure state. The second reduces valid cell ratios to
one median per dataset. The third summarizes those equally weighted dataset
values by median, IQR, and range and reports expected/paired datasets and
cells, timeouts, and out-of-memory events. External comparisons use
comparator time divided by \pkg{faissR} auto time; selector regret uses auto
time divided by empirical-oracle time. Log2 paired plots place equality at
zero. Pooled medians of elapsed seconds across heterogeneous shapes, $k$
values, metrics, or recall targets are not interpreted as speed comparisons.

CPU comparison scripts include applicable public interfaces from
\pkg{Rnanoflann}, \pkg{RANN}, \pkg{RcppAnnoy}, \pkg{RcppHNSW}, \pkg{rnndescent},
\pkg{BiocNeighbors}, \pkg{FNN}, \pkg{nabor}, and \pkg{uwot}. The CUDA audit
also records \pkg{cuda.ml}, but its current public KNN interface fits
supervised prediction models and does not return self-KNN index and distance
matrices (version 0.3.3 documentation); it is therefore marked non-standalone rather than
timed as a different task. A comparator is timed only when its public interface
can express the same metric, $k$, and self-exclusion convention. CPU and CUDA
are reported separately. Allocated and requested threads, threading scope,
conversion, index-build inclusion, result residency, and failure/timeout state
accompany elapsed time. Exact/Flat/brute-force routes are not counted as three independent
mathematical algorithms when they resolve to the same exhaustive provider;
their user-visible wrappers may still be profiled to quantify interface and
resource-reuse overhead.
These comparator packages are dependencies of the frozen benchmark image only;
they are not runtime, compilation, or fallback dependencies of \pkg{faissR}.

Provider-specific distances are converted to the public \pkg{faissR} metric
scale inside the timed adapter. Distance-error diagnostics then match candidate
and reference entries by neighbor identifier and use only identifiers present
in both sets. Set recall is reported separately and penalizes missing reference
neighbors. This avoids comparing unrelated distances merely because they occupy
the same rank and makes a permutation of an otherwise identical neighbor set
distance-error neutral.

\section{Replication files and remaining gates}

The package repository contains the JSS source, vignette, reference
documentation, benchmark launchers, exact-reference builders, conformance
suite, systems-ablation suite, publication aggregator, leave-one-dataset-out
analysis, and figure builder. Every eligible result must carry the dataset
fingerprint, requested and resolved route, metric, $k$, recall target, timing
repeat, and error state.

The held-out aggregator also writes
\path{jss_selection_stability_replicates.csv},
\path{jss_selection_stability_cells.csv}, and
\path{jss_selection_stability_summary.csv}. These preserve the
replicate-specific eligible winner and the cell- and stratum-level stability
statistics rather than reporting only the calibration winner.

The leave-one-dataset-out analysis writes three machine-readable tables. The
cell table records the cross-fitted selected family, held-out route, exact or
approximate quality classification, empirical oracle, selected/oracle time
ratio, route-family agreement, and abstention. The dataset table reports
attainment, agreement, abstention, and exact-selection frequencies for each
omitted dataset. The backend--metric--target summary reports the same
quantities across held-out datasets. An operating point is attained only when
the held-out route is complete and either exact-audited or, for an approximate
route, its mean query recall@k reaches the requested threshold in every
prespecified replicate. The minimum query recall remains diagnostic. Results
from the installed full-calibration \method{auto} policy occupy separate
columns and are not interpreted as cross-fitted evidence.

The practical Letter Recognition example in Section~6 is independently
executable as \path{manuscript/jss/practical_cpu_example.R}. It requires the
optional \pkg{mlbench} package, uses the documented 16,000/4,000 split, and
writes the three auto-operating-point rows, fitted-index timing summary, and
session provenance when \code{FAISSR\_JSS\_EXAMPLE\_OUT} is set. The reported
elapsed values are local illustrative measurements and are not merged into the
frozen comparative benchmark.

The compact entry point \path{manuscript/jss/code.R} runs on a regular CPU
computer with FAISS and \pkg{faissR} installed and delegates to the
authoritative validator \path{replication_article.R}. It executes the article
examples, checks dimensions and finite values, writes a compact summary, and
records \code{sessionInfo()}; the executed \path{code.html} exposes those
outputs for direct comparison by reviewers. If
\code{FAISSR\_JSS\_RESULTS\_DIR} identifies the frozen archive, the same entry
point verifies every source file's schema,
retains and checksums every raw rerun, selects the newest timestamped run per
method cell, rejects duplicate benchmark keys within that selected evidence,
optionally matches dataset fingerprints to
\code{FAISSR\_JSS\_DATASET\_MANIFEST}, optionally verifies the SHA-256 ledger
in \code{FAISSR\_JSS\_RESULT\_CHECKSUMS}, and regenerates held-out tables
without launching Slurm. Full
computation is reproduced separately with
\path{benchmark_scripts/jss_reproduction/final_campaign/}%
\path{submission_commands.txt};
the campaign contains 203 independent jobs so one failure cannot erase the
other method/backend evidence.
The companion \path{submit_campaign.R} program is the single commented HPC
entry point. It preflights the image, submits those unchanged launchers one at
a time for an explicitly named phase, and saves the returned Slurm identifiers
with the package/image identity. Phase advancement remains manual so failed QA,
reference, calibration, or aggregation gates cannot be bypassed accidentally.
The ledger is updated after every submission, including a failure record when
Slurm rejects a later launcher, so accepted jobs remain identifiable and are
not blindly duplicated on retry.
Before submission, the companion \path{sync_publication_suite.sh} deployment
utility can copy the suite to a user-supplied HPC mirror and verifies the
203-launcher count, submitter checksum, and shell syntax without deleting
target files.
The 203 jobs comprise 4 exact-reference, 63 calibration, 113 held-out,
12 reusable external-index, 2 systems-ablation, 2 installed-package route-QA,
and 7 audit/analysis/freeze jobs. The reusable-index diagnostic uses the same
independent exact-reference query rows (up to 1,024), reports conversion,
construction, first-query, and three repeated-query timings separately, and
does not mix its sampled-query times with the primary full all-row cold
comparison.
For the held-out aggregate, each timestamped method output directory is one
run. The newest run is selected without pooling earlier reruns, and a
publication-eligible cell must contain exactly one successful observation for
every prespecified validation-seed/repeat pair. Every observation must meet the
requested recall target.
Generated launcher and campaign-source manifests record both MD5 identity keys
and SHA-256 integrity digests. The installed-package CPU/CUDA route jobs check
the exact \pkg{faissR} version and inventory \pkg{float},
\pkg{Rnanoflann}, \pkg{RANN}, \pkg{RcppAnnoy}, \pkg{RcppHNSW},
\pkg{rnndescent}, \pkg{BiocNeighbors}, \pkg{FNN}, \pkg{nabor}, and
\pkg{uwot} with their installed versions. Both jobs retain the container
SHA-256 digest. The CUDA job additionally requires CUDA, FAISS-GPU, and cuVS
and passes a \pkg{float} matrix to \code{nn\_gpu()}; it rejects a result that
is not represented by owning CUDA buffers, reports any device-to-host result
copy, or reports compatibility double-to-float conversion. Grid, NN-descent,
NSG, and Vamana are checked
with self-query fixtures, while methods that accept independent queries use a
separate-query fixture; all fixtures use \pkg{float} reference/query matrices.
Every capability-declared unsupported method--metric cell is retained as an
explicit unsupported row rather than an execution failure. These are campaign
smoke and contract checks. CPU QA also invokes each eligible external method
through its exported public API on a small deterministic fixture and checks
dimensions, finite sorted distances, and self-neighbor exclusion. If an
installed package exposes no public standalone KNN-result API, the cell is
recorded as \code{not\_public\_api}; namespace internals are not timed.
These checks do not replace platform-specific package installation, unit-test, and
package-check reports.
Every generated launcher rejects a same-version image when its embedded
\code{FAISSR\_IMAGE\_COMMIT} differs from the required 40-character source
commit. The strict freeze audit additionally rejects held-out \pkg{faissR} rows
from an unknown or different package version, requires the package and image
commit columns on every raw result row, and verifies that both canonical
40-character values equal the requested campaign commit. It also loads every
referenced exact-neighbor object and applies the same identity check before
accepting the archive. A canonical 64-character container SHA-256 identifier is
required separately.
The final archive groups the reproducibility metadata into five tables:
(i) dataset source, release, dimensions, preprocessing, redistribution terms,
and fingerprint; (ii) package, compiler, FAISS, CUDA, cuVS, driver, and
container versions; (iii) requested and resolved method/provider/backend;
(iv) timing protocol, repeat, allocated/requested threads, threading scope,
residency, and
copy counts; and (v) failures, timeouts, unsupported contracts, exact-audit
basis, and approximate recall-target attainment. MD5 is retained only for local row identity, while SHA-256
protects submitted and externally distributed artifacts.

The installed \path{faissR\_api.h} header defines typed accessors for the
three nearest-neighbor C-callables and an ABI-version query returning one.
The external-pointer handle in a \code{faissR\_gpu\_knn} object owns its CUDA
buffers and must remain protected while a downstream package accesses either
device pointer.

\section{Interpretation}

The frozen evidence supports the package's metric and routing contracts,
reference integrity, and the observed target attainment of the completed
held-out streams. It does not yet establish a universal real-dataset speed
winner or that \method{auto} approaches an empirical oracle; those claims
require completion and aggregation of the remaining explicit-method runs. The
article and supplement preserve this distinction between calibration,
correctness, and comparative performance.
